# 项目需求规格

> 依据 2026-11-26 与孔丁科老师的对话确认。
> 本文定义**做什么**；`PROJECT_WORKFLOW.md` 定义**分几步做**；`TEAM_DIVISION.md` 定义**谁做**。

---

## 一、项目定位

老师原话：

> 该项目是一个**自动化的通用 SE workflow**，主要**通过多方 agent 与用户的交互**来完成。

关键词拆解：

| 关键词 | 含义 | 对我们意味着什么 |
|---|---|---|
| **自动化** | 流程由系统驱动，不是人手动串每一步 | 编排器是核心，不能只是"展示图" |
| **通用** | 不绑定某个具体业务领域 | 失物招领只是 fixture，不是产品 |
| **SE workflow** | 软件工程的完整流程，不是通用聊天 | 各阶段产物要符合 SE 规范 |
| **多方 agent** | 多个角色协作，不是单个模型包打天下 | 讨论阶段必须有真正的多角色 |
| **与用户的交互** | 用户全程参与，不是一次性输入 | **贯穿三个阶段**，不是某一阶段的特例 |

## 二、三级结构：三个课堂作业 = 三个递进阶段

```text
┌──────────────────────────────────────────────────────────────┐
│ 阶段 1：用户需求 → 设计规格                                    │
│   用户输入需求                                                   │
│     ↓                                                            │
│   多方 agent 讨论（可采用 autogen2）                              │
│     ↓  ←──── 用户随时介入                                       │
│   产出：设计规格（可细化，也可先出建设方案→需求规格→设计规格）      │
└──────────────────────────────────────────────────────────────┘
                          ↓ 设计规格
┌──────────────────────────────────────────────────────────────┐
│ 阶段 2：设计规格 → 可视化编排器                                 │
│   输入阶段 1 的设计规格                                          │
│     ↓                                                            │
│   不断分解任务                                                   │
│     ↓  ←──── 用户可随时交互（编辑各节点关系）                     │
│   生成可编辑的可视化编排器                                       │
│     ↓                                                            │
│   **不止编排，还要推到执行**                                      │
└──────────────────────────────────────────────────────────────┘
                          ↓ 编排过程 + 执行过程
┌──────────────────────────────────────────────────────────────┐
│ 阶段 3：可观测性框架                                             │
│   阶段 1、2 的可视化部分（收编）                                  │
│   + 执行过程中哪些数据需要记录、怎么展示                          │
│   + 执行交互（比如圆桌交互）                                      │
│   + 事后回溯                                                     │
└──────────────────────────────────────────────────────────────┘
```

## 三、阶段 1 需求：用户需求 → 设计规格

### 3.1 老师的明确要求

> 阶段 1 是通过用户输入的需求，通过多方 agent 讨论（可采用 autogen2 的方式），与用户不断进行交互，得到一个细化完善的设计规格。

### 3.2 功能需求

| # | 需求 | 说明 | 优先级 |
|---|---|---|---|
| **1-1** | 用户输入需求 | 一句话想法即可，系统要能追问 | P0 |
| **1-2** | 多方 agent 讨论 | 多角色、有独立发散、有批判，不能是单模型自问自答 | P0 |
| **1-3** | **与用户不断交互** | 讨论过程中用户可随时介入、补充、纠正 | **P0（核心）** |
| **1-4** | 产出设计规格 | 细化完善，可作为阶段 2 的输入 | P0 |
| **1-5** | 讨论过程可视化 | 见 3.4 | P0 |
| **1-6** | 支持分阶段收敛 | 可先出建设方案 → 需求规格 → 设计规格，也可一步直达 | P1 |
| 1-7 | 可采用 autogen2 | 推荐方式，非强制 | P2 |

### 3.3 关于「分阶段 vs 一步到位」（老师的重要补充）

老师给出了**弹性设计**：

> 大体没问题，具体课上可以多聊聊。这部分不一定直接讨论出设计规格，**可以细化，可以先讨论出建设方案，转为需求规格（需要确认），再到设计规格（需要评审）**，之后可以转入作业 2 实现环节。

> 是否需要这么细**取决于项目类型和规模**

> 一般小项目才会靠一个会直接讨论出设计规格

> 我们设计流程肯定要**向下兼容**，不可能只支持上

> 而且多智能体群体会议讨论**不适宜讨论过长**，容易挤爆智能体的上下文又引起不必要的幻觉

> 所以**分段**是个很有效的方式

**这意味着**：

| 项目规模 | 流程 |
|---|---|
| 小项目 | 讨论 → 直接出设计规格（一步） |
| 中大型 | 讨论 → 建设方案 → 需求规格（需确认）→ 设计规格（需评审）→ 阶段 2 |

**需求 1-6 的准确表述**：系统必须支持「分阶段收敛」，且**向下兼容**（简单项目可用简化流程）。

### 3.4 阶段 1 的可视化要求（老师原话）

> 可视化就是能看到 **agent 讨论过程**（就比如平时使用 agent 能够看到它的**思考过程**），**增删，评分**等等。**需求规格，设计规格都能被直接看见**。**用户可随时与系统交互**。

拆成可验收项：

| # | 需求 | 当前状态 |
|---|---|---|
| a | 看到 agent 的思考过程 | ❌ 无 |
| b | 增删（观点/异议的增删） | ❌ 无 |
| c | 评分 | ⚠️ 有 B06 共识评价，未可视化 |
| d | 需求规格可直接看见 | ✅ 有（03 页） |
| e | 设计规格可直接看见 | ✅ 有（04 页） |
| f | **用户可随时与系统交互** | ❌ 无（只有两个固定介入点） |

## 四、阶段 2 需求：设计规格 → 可视化编排器 + 执行

### 4.1 老师的明确要求

> 阶段 2 是输入阶段 1 的设计规格，通过**不断分解任务**，并且**用户能随时进行交互（编辑各节点关系等）** 最终生成一个**可视化的编排器**。

**老师补充的关键一句**：

> **不止编排，还要推到执行**

### 4.2 功能需求

| # | 需求 | 说明 | 优先级 |
|---|---|---|---|
| **2-1** | 输入设计规格 | 消费阶段 1 的产出；也支持外部规格独立测试 | P0 |
| **2-2** | 不断分解任务 | 可增量分解、可重新分解，不是一次性 | P0 |
| **2-3** | **用户可随时交互编辑节点关系** | 增删任务、改依赖、改验收条件 | **P0（核心）** |
| **2-4** | 可视化编排器 | 见 4.3 | P0 |
| **2-5** | **推到执行** | 不只是画图，要真的执行 | **P0** |
| 2-6 | 执行可视化 | 执行状态、进度、产物 | P0 |
| 2-7 | 执行控制 | 暂停/继续/中止 | P1 |

### 4.3 可视化编排器的具体要求

| # | 要求 | 当前状态 |
|---|---|---|
| a | 任务节点可见（依赖、状态、耗时） | ✅ 有 |
| b | 图布局清晰 | ✅ 有（dagre 分层） |
| c | **可编辑节点关系** | ❌ **无**（React Flow 有 `onNodesChange`，但 `useEffect` 每次覆盖布局，编辑无法保存） |
| d | 可增删任务 | ❌ 无 |
| e | 并行批次显示 | ⚠️ 有拓扑序，无批次视图 |
| f | 执行状态回显 | ✅ 有 |

### 4.4 关于「推到执行」的边界

老师原话：

> 光设计流程有啥用，肯定要**跑案例项目啊**，通过案例优化流程，课上提了好多次了，比如**先跑通四则混合运算**

**这说明**：

1. 执行必须是**真实的**，不是 mock
2. 需要准备**案例项目**（如四则混合运算计算器）
3. 流程要通过跑案例来优化

**当前差距**：`default_stack()` 默认 `execution_mode="mock"`，执行结果标注 `simulated=True`。

## 五、阶段 3 需求：可观测性框架

### 5.1 老师的明确要求

> 另外 2 个人可以做**作业 3 的内容**，除了 1、2 的可视化部分，主要是**设计和实现执行过程中哪些数据需要记录、怎么展示**，也包括**执行交互部分**，比如**圆桌交互**，这些都属于作业 3 需要考虑的内容。

### 5.2 功能需求

| # | 需求 | 说明 | 优先级 |
|---|---|---|---|
| **3-1** | 收编阶段 1、2 的可视化 | 统一表达，不是各做各的 | P0 |
| **3-2** | **定义执行过程中记录哪些数据** | 观测数据的 schema | **P0（老师点名）** |
| **3-3** | **怎么展示这些数据** | 观测视图 | **P0** |
| **3-4** | **执行交互** | 如**圆桌交互** | **P0（老师点名）** |
| 3-5 | 事后回溯 | 复盘分析 | P1 |

### 5.3 关于「圆桌交互」

老师用词是「比如圆桌交互」。结合阶段 1 的「多方 agent 讨论」，我理解是：

> 多个 agent 与用户围坐讨论，用户可以点名某个 agent 发言、追问、质疑，而不是被动看结果。

这一点需要与老师确认（见 `OPEN_QUESTIONS.md`）。

### 5.4 关于「阶段 3 与阶段 1/2 的重叠」

老师解释得很清楚：

> 可视化部分**分割到 1/2 去**

即：**阶段 1、2 各自做自己的可视化**，阶段 3 做的是：

1. 把 1、2 的可视化**统一**（框架层面）
2. **额外**的观测数据设计
3. **额外**的执行交互

**不是重复做，是分层**。老师用了一个比喻：

> 我提的分工想法是因为可视化部分又不影响 12 流程的优化，可以独立为 3，比如，**你装修一个会议室又不影响你会议流程，等装修好了再搬到新会议室就行**。

## 六、贯穿三阶段的核心原则

### 6.1 「先跑通再迭代优化」

老师在对话结尾的原话：

> **不用太急，多想想，先跑通再迭代优化**

以及：

> 我们后续肯定都是通过**跑项目案例，迭代优化流程**，不然空对空没有任何实际意义

**这改变了我们的排期策略**：

| 原策略 | 新策略 |
|---|---|
| 每个功能做到完美再进入下一个 | **先跑通一个端到端案例，再迭代** |
| 按模块并行开发 | **先打通一条链路，再按需扩宽** |

### 6.2 「向下兼容」

老师强调：

> 我们设计流程肯定要**向下兼容**，不可能只支持上

**含义**：流程设计要支持从「简单一步到位」到「完整分阶段」的整个谱系，不能只支持最复杂的那种。

### 6.3 「分段是有效方式」

老师对长讨论的担忧：

> 多智能体群体会议讨论**不适宜讨论过长**，容易**挤爆智能体的上下文**又引起**不必要的幻觉**

**这是设计约束**，不是建议。意味着：
- 讨论必须分段
- 每段要有明确的收敛条件
- 不能无限轮次

## 十、与现有实现的关系

当前仓库已实现的能力与本文需求的对应：

| 阶段 | 已有 | 缺失（P0） |
|---|---|---|
| 1 | 讨论状态机 A—H、四角色、六人确认、R1、真实模型接入 | **用户随时的交互**、设计规格细化、思考过程可视化 |
| 2 | 设计规格输入、动态分解、九态编排、DAG/甘特/时间线/事件流 | **节点关系编辑**、**真实执行**、增量分解 |
| 3 | 八页面工作台、事件流、任务详情、Agent 执行中心 | **观测数据 schema**、**执行交互（圆桌）**、事后回溯 |

**结论**：骨架完整，缺的是「交互」这条主线——三个阶段都缺用户交互。
