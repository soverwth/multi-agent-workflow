## 一、项目定位

老师原话：

> 该项目是一个**自动化的通用 SE workflow**，主要**通过多方 agent 与用户的交互**来完成。

**第二轮确认（关键）**：

> 该项目是**全自动化的，没有人工介入**，只有**用户与系统中多个 agent 进行交互**。

关键词拆解：

| 关键词 | 含义 | 对我们意味着什么 |
|---|---|---|
| **自动化** | 流程由系统驱动 | 编排器是核心，不能只是"展示图" |
| **没有人工介入** | **不设审批门**，流程不因等人而暂停 | 现有 3 处 `WAITING_HUMAN` 必须改造 |
| **通用** | 不绑定具体业务领域 | 先做通用框架，案例只用于测试 |
| **SE workflow** | 软件工程的完整流程 | 各阶段产物要符合 SE 规范 |
| **多方 agent** | 多角色协作 | 讨论阶段必须有真正的多角色 |
| **用户与 agent 交互** | 用户实时对话，**但不是审批** | 交互是并行的，不是阻塞的 |

### 1.1 「人工介入」与「用户交互」的区别（务必分清）

这两个概念容易混淆，但在本项目里是**相反**的：

| | 人工介入 | 用户与 agent 交互 |
|---|---|---|
| 流程是否暂停 | **是**（等人操作） | **否**（agent 继续，用户随时插话） |
| 用户做什么 | 审批、勾选、裁决 | 提需求、追问、质疑、补充 |
| 项目是否采用 | ❌ **不采用** | ✅ **核心机制** |
| 现有实现 | 3 处 `WAITING_HUMAN` | 基本没有 |

**结论**：项目要的是「用户能随时和 agent 说话」，不是「流程停下来等人点按钮」。

### 1.2 用户交互的四条实现约束（第二轮确认）

用户对「圆桌交互」的四个细节给出了明确答复：

| # | 问题 | 答复 | 实现含义 |
|---|---|---|---|
| a | 打断式还是并行式？ | **两种都行，选实现简单的** | 建议选**并行式**（非阻塞），实现更简单：用户消息入队，agent 在阶段边界读取 |
| b | 用户能否修改 agent 产出？ | **可以修改** | 需要「用户编辑」的写回路径 + 版本记录 |
| c | 用户长时间不回应怎么办？ | **继续按推荐的跑** | **默认超时继续**，不阻塞 |
| d | 交互历史是否要持久化？ | **需要，可采用 SQL 记忆** | 需要对话记忆表 |

**关于 1.2a 的选型建议**

用户说「两种都行，选实现简单的」。我建议选**并行式**：

| | 并行式（推荐） | 打断式 |
|---|---|---|
| 实现复杂度 | 低：消息入队，阶段边界消费 | 高：需要中断正在执行的 agent |
| 与「无人工介入」的一致性 | ✅ 天然一致 | ⚠️ 打断本身近似人工介入 |
| 用户体验 | 用户说话后可能等一会才生效 | 立即响应 |
| 风险 | 用户可能觉得"没反应" | 打断后状态恢复易出错 |

**并行式的具体机制**：

```text
用户发消息
   ↓
写入对话记忆表（SQL）
   ↓
标记「有待消费的用户输入」
   ↓
当前阶段跑完后，在阶段边界读取并应用
   ↓
继续下一阶段
```

**这样用户不需要等 agent，agent 也不打断**。

### 1.3 对话记忆的设计（1.2d）

用户明确「可采用 SQL 记忆」。

**建议的表结构**（可放在 B03 的 `blackboard.db` 或 `platform.db`）：

```sql
CREATE TABLE IF NOT EXISTS conversation_messages (
    message_id   TEXT PRIMARY KEY,
    run_id       TEXT NOT NULL,          -- 关联的讨论运行
    stage        TEXT,                   -- 产生时的阶段（A—H）
    role         TEXT NOT NULL,          -- 'user' | 'agent:<role_id>' | 'system'
    content      TEXT NOT NULL,
    created_at   TEXT NOT NULL,
    consumed_at  TEXT,                   -- agent 何时消费了这条用户输入
    applied_to   TEXT                    -- 应用到哪个产物（如 r1/design_spec 的版本）
);
```

**要点**：
- `consumed_at` 为空 = 尚未被 agent 消费（用于并行式）
- `applied_to` 记录这条输入影响了哪个产物版本（可追溯）
- 与现有 `task_run_events` 分开：对话是「输入」，事件是「状态变化」

**现有可复用的基础设施**：B03 的 `TaskStateStore` 已经用 SQLite，新增一张表即可。

## 二、三级结构：三个课堂作业 = 三个递进阶段

```text
┌──────────────────────────────────────────────────────────────┐
│ 阶段 1：用户需求 → 设计规格                                    │
│   用户输入需求                                                   │
│     ↓                                                            │
│   多方 agent 讨论（可采用 autogen2）                              │
│     ↓  ←──── 用户随时介入                                       │
│   产出：设计规格（可细化，也可先出建设方案→需求规格→设计规格）      │
└──────────────────────────────────────────────────────────────┘
                          ↓ 设计规格
┌──────────────────────────────────────────────────────────────┐
│ 阶段 2：设计规格 → 可视化编排器                                 │
│   输入阶段 1 的设计规格                                          │
│     ↓                                                            │
│   不断分解任务                                                   │
│     ↓  ←──── 用户可随时交互（编辑各节点关系）                     │
│   生成可编辑的可视化编排器                                       │
│     ↓                                                            │
│   **不止编排，还要推到执行**                                      │
└──────────────────────────────────────────────────────────────┘
                          ↓ 编排过程 + 执行过程
┌──────────────────────────────────────────────────────────────┐
│ 阶段 3：可观测性框架                                             │
│   阶段 1、2 的可视化部分（收编）                                  │
│   + 执行过程中哪些数据需要记录、怎么展示                          │
│   + 执行交互（比如圆桌交互）                                      │
│   + 事后回溯                                                     │
└──────────────────────────────────────────────────────────────┘
```

## 三、阶段 1 需求：用户需求 → 设计规格

### 3.1 老师的明确要求

> 阶段 1 是通过用户输入的需求，通过多方 agent 讨论（可采用 autogen2 的方式），与用户不断进行交互，得到一个细化完善的设计规格。

### 3.2 功能需求

| # | 需求 | 说明 | 优先级 |
|---|---|---|---|
| **1-1** | 用户输入需求 | 一句话想法即可，系统要能追问 | P0 |
| **1-2** | 多方 agent 讨论 | 多角色、有独立发散、有批判，不能是单模型自问自答 | P0 |
| **1-3** | **用户与 agent 实时交互** | 用户可随时插话、追问、质疑、补充；**流程不暂停等人** | **P0（核心）** |
| **1-4** | 产出**尽可能细化**的设计规格 | 见 3.5 的细化标准 | P0 |
| **1-5** | 讨论过程可视化 | 见 3.4 | P0 |
| **1-6** | 支持分阶段收敛（向下兼容） | 可先出建设方案 → 需求规格 → 设计规格，也可一步直达 | P1 |
| **1-7** | **无人工审批门** | agent 自主推进，用户不做勾选式审批 | **P0** |
| 1-8 | 可采用 autogen2 | 推荐方式，非强制 | P2 |

### 3.3 关于「分阶段 vs 一步到位」（老师的重要补充）

老师给出了**弹性设计**：

> 大体没问题，具体课上可以多聊聊。这部分不一定直接讨论出设计规格，**可以细化，可以先讨论出建设方案，转为需求规格（需要确认），再到设计规格（需要评审）**，之后可以转入作业 2 实现环节。

> 是否需要这么细**取决于项目类型和规模**

> 一般小项目才会靠一个会直接讨论出设计规格

> 我们设计流程肯定要**向下兼容**，不可能只支持上

> 而且多智能体群体会议讨论**不适宜讨论过长**，容易挤爆智能体的上下文又引起不必要的幻觉

> 所以**分段**是个很有效的方式

**这意味着**：

| 项目规模 | 流程 |
|---|---|
| 小项目 | 讨论 → 直接出设计规格（一步） |
| 中大型 | 讨论 → 建设方案 → 需求规格（需确认）→ 设计规格（需评审）→ 阶段 2 |

**需求 1-6 的准确表述**：系统必须支持「分阶段收敛」，且**向下兼容**（简单项目可用简化流程）。

### 3.4 阶段 1 的可视化要求（老师原话）

> 可视化就是能看到 **agent 讨论过程**（就比如平时使用 agent 能够看到它的**思考过程**），**增删，评分**等等。**需求规格，设计规格都能被直接看见**。**用户可随时与系统交互**。

拆成可验收项：

| # | 需求 | 当前状态 |
|---|---|---|
| a | 看到 agent 的思考过程 | ❌ 无 |
| b | 增删（观点/异议的增删） | ❌ 无 |
| c | 评分 | ⚠️ 有 B06 共识评价，未可视化 |
| d | 需求规格可直接看见 | ✅ 有（03 页） |
| e | 设计规格可直接看见 | ✅ 有（04 页） |
| f | **用户可随时与系统交互** | ❌ 无（且现有的是审批门，要改造） |

### 3.5 设计规格的细化标准（Q4：尽可能细化）

老师明确要求「设计规格**尽可能细化**」。

当前 `phase_bridge.py` 的产出远远不够：

```python
"contract": {
    "operations": [],        # 空
    "errors": {},            # 空
    "field_bounds": {},      # 空
    "response_envelope": {}, # 空
}
"design_entries": [{
    "contract_refs": [],     # 空
    "rule": "具体技术方案由设计规格评审补充。",  # 占位文字
}]
```

**「尽可能细化」应达到的标准**：

| 部分 | 内容要求 | 现状 |
|---|---|---|
| 需求条目 | req_id、标题、描述、优先级、验收条件、约束 | ✅ 有 |
| **接口定义** | operations：名称、方法、路径、鉴权、请求字段、响应字段、状态码 | ❌ **必补** |
| **错误码** | 错误码 → HTTP 状态码映射 | ❌ **必补** |
| **字段边界** | 每个字段的长度、格式、必填性、取值范围 | ❌ **必补** |
| **响应结构** | 统一响应 envelope（data / error / meta） | ❌ **必补** |
| **数据模型** | 实体、字段、关系、索引 | ❌ **必补** |
| **设计条目** | design_id → 模块 → 需求引用 → 契约引用 → 测试引用 | ⚠️ 有但引用全空 |
| **非功能约束** | 性能、安全、并发要求 | ❌ 无 |

**参考**：SE-lib 的 `docs/contracts/design-spec.schema.json` 可作为字段组织的蓝本（详见 `REFERENCE_PROJECTS.md` 3.2）。

## 四、阶段 2 需求：设计规格 → 可视化编排器 + 执行

### 4.1 老师的明确要求

> 阶段 2 是输入阶段 1 的设计规格，通过**不断分解任务**，并且**用户能随时进行交互（编辑各节点关系等）** 最终生成一个**可视化的编排器**。

**老师补充的关键一句**：

> **不止编排，还要推到执行**

### 4.2 功能需求

| # | 需求 | 说明 | 优先级 |
|---|---|---|---|
| **2-1** | 输入设计规格 | 消费阶段 1 的产出；也支持外部规格独立测试 | P0 |
| **2-2** | 不断分解任务 | 可增量分解、可重新分解，不是一次性。**现状核实（2026-11-27）：`dynamic_planner.build_tasks_from_spec` 只是规则查表（设计条目/契约操作/需求各→1 任务），没有分解逻辑** → 由分工 C-7（分解模块）+ C-5（增量重算）承接 | P0 |
| **2-3** | **用户可随时交互编辑节点关系** | 增删任务、改依赖、改验收条件 | **P0（核心）** |
| **2-4** | 可视化编排器 | 见 4.3 | P0 |
| **2-5** | **推到执行** | 不只是画图，要真的执行 | **P0** |
| 2-6 | 执行可视化 | 执行状态、进度、产物 | P0 |
| 2-7 | 执行控制 | 暂停/继续/中止 | P1 |

### 4.3 可视化编排器的具体要求

| # | 要求 | 当前状态 |
|---|---|---|

### 4.4 「推到执行」的明确边界（Q3：产出网页端软件）

### 4.7 案例成熟度分级（重新定义）

既然现有案例都不完整，需要重新定义成熟度：

| 级别 | 定义 | 判定标准 |

## 五、阶段 3 需求：可观测性框架

### 5.1 老师的明确要求

> 另外 2 个人可以做**作业 3 的内容**，除了 1、2 的可视化部分，主要是**设计和实现执行过程中哪些数据需要记录、怎么展示**，也包括**执行交互部分**，比如**圆桌交互**，这些都属于作业 3 需要考虑的内容。

### 5.2 功能需求

| # | 需求 | 说明 | 优先级 |
|---|---|---|---|
| **3-1** | 收编阶段 1、2 的可视化 | 统一表达，不是各做各的 | P0 |
| **3-2** | **定义执行过程中记录哪些数据** | 观测数据的 schema | **P0（老师点名）** |
| **3-3** | **怎么展示这些数据** | 观测视图 | **P0** |
| **3-4** | **执行交互** | 如**圆桌交互** | **P0（老师点名）** |
| 3-5 | 事后回溯 | 复盘分析 | P1 |

### 5.3 关于「圆桌交互」

老师回答 Q1 时明确了最关键的一点：

> 该项目是**全自动化的，没有人工介入**，只有**用户与系统中多个 agent 进行交互**。

**「圆桌交互」的准确定义**

多个 agent 与用户在**同一个界面**中协作，用户可以：

- 点名某个 agent 发言
- 追问某个观点
- 质疑并要求举证
- 让两个 agent 辩论
- 补充需求、纠正方向

**关键约束（必须遵守）**

| 约束 | 含义 |
|---|---|
| **流程不因用户不响应而暂停** | 交互是并行的、非阻塞的 |
| **不设审批按钮** | 用户不点"同意"，agent 自主推进 |
| **交互是一等公民** | 不是附属功能，是核心机制 |

**与现有实现的冲突**

现有 B02 讨论状态机有 3 处 `WAITING_HUMAN`，属于**审批门**，与「没有人工介入」直接矛盾，必须改造：

| 位置 | 现有行为 | 改造方向 |
|---|---|---|
| `controller.py:170` | EVALUATE 有分歧 → `WAITING_HUMAN` | agent 辩论 + 自动判定 |
| `controller.py:195` | Proposal 被拒 → `WAITING_HUMAN` | 自动修订重试（有限轮次） |
| `controller.py:208` | HUMAN_CONFIRMATION → 等六人勾选 | **改为 agent 互相确认** |

### 5.4 关于「阶段 3 与阶段 1/2 的重叠」

老师解释得很清楚：

> 可视化部分**分割到 1/2 去**

即：**阶段 1、2 各自做自己的可视化**，阶段 3 做的是：

1. 把 1、2 的可视化**统一**（框架层面）
2. **额外**的观测数据设计
3. **额外**的执行交互

**不是重复做，是分层**。老师用了一个比喻：

> 我提的分工想法是因为可视化部分又不影响 12 流程的优化，可以独立为 3，比如，**你装修一个会议室又不影响你会议流程，等装修好了再搬到新会议室就行**。

## 六、贯穿三阶段的核心原则

### 6.1 「先跑通再迭代优化」

老师在对话结尾的原话：

> **不用太急，多想想，先跑通再迭代优化**

以及：

> 我们后续肯定都是通过**跑项目案例，迭代优化流程**，不然空对空没有任何实际意义

**这改变了我们的排期策略**：

| 原策略 | 新策略 |
|---|---|
| 每个功能做到完美再进入下一个 | **先跑通一个端到端案例，再迭代** |
| 按模块并行开发 | **先打通一条链路，再按需扩宽** |

### 6.2 「向下兼容」

老师强调：

> 我们设计流程肯定要**向下兼容**，不可能只支持上

**含义**：流程设计要支持从「简单一步到位」到「完整分阶段」的整个谱系，不能只支持最复杂的那种。

### 6.3 「分段是有效方式」

老师对长讨论的担忧：

> 多智能体群体会议讨论**不适宜讨论过长**，容易**挤爆智能体的上下文**又引起**不必要的幻觉**

**这是设计约束**，不是建议。意味着：
- 讨论必须分段
- 每段要有明确的收敛条件
- 不能无限轮次
