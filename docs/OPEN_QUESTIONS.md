## 一、需要问老师

### Q0【最高优先，新】「与用户多次交互」具体到几次、在哪几步？

**背景**

用户澄清作业 1 的关键要求：

> 用户输入一个需求，最后输出一个需求规格（设计规格）。通过多智能体讨论（可采用 Autogen2）是完成这个任务推荐的一个方式。**中途需要与用户进行多次交互**。

**现状**

当前只有**两个**人工介入点：

| 介入点 | 触发条件 | 用户能做什么 |
|---|---|---|
| 人类裁决 | 出现高影响价值分歧 | 填写裁决内容 |
| 六人确认 | 需求草案生成后 | 六名成员勾选确认（不能改内容） |

**缺的是**：讨论中途与用户**多轮对话**的能力——用户表达一句模糊需求，系统问"你指的是什么"，用户补充，再继续讨论。

**为什么重要**

这可能是作业 1 的**核心评分点**。如果老师期望的是"对话式需求澄清"，而我们现在做的是"跑一遍固定流程"，**形态就错了**。

而且这直接影响：
- 前端要不要做对话界面
- 后端要不要加"暂停讨论等用户回答"的状态
- 讨论状态机要不要加新的阶段

**建议问法**

> 作业 1 要求「中途需要与用户进行多次交互」。请问这个交互：
> 1. 大概几次？是固定几个检查点，还是不确定次数的对话？
> 2. 发生在哪些步骤？（需求澄清时？讨论出现分歧时？出方案后确认时？）
> 3. 用户能以什么形式参与？是回答问题、补充约束，还是自由对话？
> 4. 如果用户不回答，流程应该暂停等待还是继续？

### Q2【高优先】作业 2 的「控制」要到什么程度？

**背景**
作业 2 要求「执行可视化**和控制**」，作业 3 提到「执行**交互**」。用户对"执行交互"的描述是：

> 执行过程中，用户可暂停、更改，对当前 AI 给出的想法进行更正等等

但用户也表示**具体仍不清晰**（问题保留）。

**现状**
| 能力 | 讨论阶段 | 任务编排阶段 |
|---|---|---|
| 推进一步 | 有 | 有 |
| 运行至完成 | 有 | 有 |
| 暂停 / 恢复 | **有** | **无** |
| 人工裁决 | 有 | 无 |
| 中止 / 改派 / 跳过验收 | 无 | 无 |

即：作业 2 的"控制"目前只有单向推进，**没有暂停/中止/改派**。

**为什么重要**
这决定了作业 2 和作业 3 的工作量量级。若要支持"执行中修改任务依赖 / 重新派发 / 人工跳过验收"，涉及状态机改造（当前九态的合法迁移表里没有这些入口），工作量远超 UI 层。

**建议问法**
> 作业 2 的「执行可视化和控制」中，"控制"是否包括：暂停 / 恢复、中止任务、修改任务依赖、重新派发、人工跳过验收？还是只要有"推进 + 观测"即可？
> 作业 3 的"执行交互"是否指执行过程中能与 Agent 对话、更正其输出？

### Q3【高优先】作业 2 的交付形态是「编排器」还是「编排出来的软件」？

**背景**
用户转述老师的话时表示不清楚，给了两种可能：
- **A**：一个可视化清晰的编排器（**产物是工具本身**）
- **B**：根据这个详细编排器执行出来的软件（**产物是被开发出来的软件**）

**现状**
- 当前编排器可演示（DAG / 甘特 / 时间线 / 事件流）
- 但执行是 **mock**（`simulated=True`），不会真的产出可运行软件

**为什么重要**
- 若 A → 现状基本够用，执行可以是 mock
- 若 B → 必须接真实 runner，且要真的让 Agent 写代码、跑测试、产出可运行程序。这是**量级完全不同**的工程

**建议问法**
> 作业 2 的交付是（A）能看到任务 DAG 与编排过程的可视化编排器，还是（B）最终能跑起来一个被开发出来的软件？如果我的想法是"做一个失物招领系统"，作业 2 的验收是看到这个系统的编排，还是要交付一个能运行的失物招领网站？

### Q4【中优先，范围已收窄】设计规格要精细到什么程度？

**背景（已按用户澄清更新）**

用户确认：作业 1 的终点就是**输出需求规格（设计规格）**，作业 2 用它当输入。所以「要不要产出设计规格」已明确——**要**。

剩余的不确定是：**要精细到什么程度**。

**现状**

`phase_bridge.py` 把 R1 转成 design spec 时：

```python
"contract": {
    "operations": [],        # 空
    "errors": {},            # 空
    "field_bounds": {},      # 空
    "response_envelope": {}, # 空
}
"design_entries": [{"contract_refs": [], "rule": "具体技术方案由设计规格评审补充。"}]
```

即：有需求列表，但**没有接口定义、错误码、字段边界**。

**为什么重要**

作业 2 的任务分解（B01）能消费需求列表（当前已能跑通：campus 24 任务 / lab 11 任务），但**要做"详细编排"就需要更细的规格**。规格精度直接决定作业 2 的任务粒度。

**建议问法**
> 作业 1 输出的设计规格，是否需要包含接口定义（operations）、错误码、字段边界这些细节？还是只要需求条目 + 验收条件就够作业 2 做任务分解？

**参考**：SE-lib 的 `docs/contracts/design-spec.schema.json` 可作为字段组织的蓝本（详见 `REFERENCE_PROJECTS.md` 第 3.2 节）。

### Q6 三个组共用同一份前端，如何协作？

**背景**
作业 1、2、3 都要可视化，而仓库只有**一份前端工程** `frontend/`（八页面工作台）。

**现状**
- 01 / 02 / 03 页偏作业 1
- 04 / 05 页偏作业 2
- 全部页面 + 06 / 07 / 08 偏作业 3

三个组如果同时改 `frontend/src/App.tsx`（目前约 1000 行），**必然冲突**。

**可选的三种做法**

| 做法 | 优点 | 缺点 |
|---|---|---|
| **A. 拆分页面到独立文件**，每个页面一个组件文件，App.tsx 只做路由 | 冲突面小，符合 React 常规 | 需要一次重构（约 4—6 小时） |
| **B. 按目录分**：`src/stages/homework1/`、`homework2/`、`homework3/` | 边界清晰 | 与现有八页面结构不一致，要重排 |
| **C. 不改结构，靠 Git 分支 + 频繁合并** | 零成本立即开工 | `App.tsx` 会反复冲突，后期痛苦 |

**建议**：先做 A（把 8 个页面各自拆成文件），再做分工。这是**唯一能让三组并行改前端而不天天冲突**的办法。

**需要你决定**：是否接受这次重构（约 4—6 小时）？

### Q7 作业 3 的「事后回溯」做到什么深度？

**背景**
用户未明确定义。老师原话是「进一步也可以考虑事后回溯等」。

| L3 | 决策对比：同一想法跑多次，对比不同分工/配置的产出差异 | 约 20h |

**建议**：L1 保底，有余力做 L2。

**需要你决定**：定在哪一档？
