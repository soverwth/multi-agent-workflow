### Q2【高优先】作业 2 的「控制」要到什么程度？

**背景**
作业 2 要求「执行可视化**和控制**」，作业 3 提到「执行**交互**」。用户对"执行交互"的描述是：

> 执行过程中，用户可暂停、更改，对当前 AI 给出的想法进行更正等等

但用户也表示**具体仍不清晰**（问题保留）。

**现状**
| 能力 | 讨论阶段 | 任务编排阶段 |
|---|---|---|
| 推进一步 | 有 | 有 |
| 运行至完成 | 有 | 有 |
| 暂停 / 恢复 | **有** | **无** |
| 人工裁决 | 有 | 无 |
| 中止 / 改派 / 跳过验收 | 无 | 无 |

即：作业 2 的"控制"目前只有单向推进，**没有暂停/中止/改派**。

**为什么重要**
这决定了作业 2 和作业 3 的工作量量级。若要支持"执行中修改任务依赖 / 重新派发 / 人工跳过验收"，涉及状态机改造（当前九态的合法迁移表里没有这些入口），工作量远超 UI 层。

**建议问法**
> 作业 2 的「执行可视化和控制」中，"控制"是否包括：暂停 / 恢复、中止任务、修改任务依赖、重新派发、人工跳过验收？还是只要有"推进 + 观测"即可？
> 作业 3 的"执行交互"是否指执行过程中能与 Agent 对话、更正其输出？

### Q6 三个组共用同一份前端，如何协作？

**背景**
作业 1、2、3 都要可视化，而仓库只有**一份前端工程** `frontend/`（八页面工作台）。

**现状**
- 01 / 02 / 03 页偏作业 1
- 04 / 05 页偏作业 2
- 全部页面 + 06 / 07 / 08 偏作业 3

三个组如果同时改 `frontend/src/App.tsx`（目前约 1000 行），**必然冲突**。

**可选的三种做法**

| 做法 | 优点 | 缺点 |
|---|---|---|
| **A. 拆分页面到独立文件**，每个页面一个组件文件，App.tsx 只做路由 | 冲突面小，符合 React 常规 | 需要一次重构（约 4—6 小时） |
| **B. 按目录分**：`src/stages/homework1/`、`homework2/`、`homework3/` | 边界清晰 | 与现有八页面结构不一致，要重排 |
| **C. 不改结构，靠 Git 分支 + 频繁合并** | 零成本立即开工 | `App.tsx` 会反复冲突，后期痛苦 |

**建议**：先做 A（把 8 个页面各自拆成文件），再做分工。这是**唯一能让三组并行改前端而不天天冲突**的办法。

**需要你决定**：是否接受这次重构（约 4—6 小时）？
