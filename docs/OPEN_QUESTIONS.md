### Q1【高优先】「圆桌交互」的技术形态细节

**已明确的部分（老师 Q1 回答）**

> 你的理解是对的，该项目是**全自动化的，没有人工介入**，只有**用户与系统中多个 agent 进行交互**。

这条回答澄清了两件不同的事：

| 概念 | 含义 | 是否存在 |
|---|---|---|
| **人工介入** | 流程暂停，等人来做审批/裁决/确认 | ❌ **不存在** |
| **用户与 agent 交互** | 用户实时和 agent 对话，agent 据此调整产出 | ✅ **存在** |

这对架构有直接影响：

- 当前 B02 讨论状态机有 3 处 `WAITING_HUMAN`（价值裁决、Proposal 审阅、六人确认），**这些人工审批门要改造**
- 「六人确认」需要重新设计：不是停下等人勾选，而是 agent 之间互相确认，用户只做对话
- 交互不能阻塞流程：用户不说话时，流程应继续；用户说话时，agent 实时响应

**仍需确认的细节**

| # | 待确认 | 为什么重要 |
|---|---|---|
| a | 交互是**打断式**还是**并行式**？ | 打断式=用户说话时流程暂停等回复；并行式=用户随时插话但流程继续跑 |
| b | 用户能否**修改 agent 已产出的内容**（如改某条需求）？ | 若可以，需要"用户编辑"的写回路径 |
| c | 用户**长时间不回应**时，流程怎么办？ | 继续跑 / 等待 / 超时降级 |
| d | 交互的历史是否要**持久化并可回溯**？ | 影响观测数据设计 |

**建议问法**
> 关于"没有人工介入、只有用户与 agent 交互"，想确认几点：
> 1. 用户说话时，agent 讨论是暂停等他，还是继续跑、用户随时插话？
> 2. 用户能否直接修改 agent 已经产出的需求条目/任务节点？
> 3. 用户长时间不回应，流程是等待还是继续推进？

## 三、「没有人工介入」带来的重大改造

这是本轮最重要的发现，单独列出。

### 3.1 现状：3 处人工审批门

`b02-workflow-agent/backend/controller.py`：

| 位置 | 触发条件 | 当前行为 |
|---|---|---|
| `:170` | EVALUATE 阶段有高影响价值分歧 | `WAITING_HUMAN` + `HUMAN_DECISION_REQUIRED` |
| `:195` | PROPOSAL_REVIEW 阶段审阅被拒 | `WAITING_HUMAN` + `HUMAN_DECISION_REQUIRED` |
| `:208` | HUMAN_CONFIRMATION 阶段 | 等六人勾选确认 |

### 3.2 目标：零人工审批门

| 现有门 | 改造方向 |
|---|---|
| 价值分歧裁决 | agent 之间辩论 + 用户对话中表态，不设审批门 |
| Proposal 审阅被拒 | agent 自动修订重试（有限轮次） |
| **六人确认** | **改为 agent 互相确认**；用户通过对话参与，但不做勾选式审批 |

### 3.3 「六人确认」的设计难点

这是最需要重新设计的部分。当前的语义是：
- 六名人类成员分别确认
- 不足六人不发 R1

新语义应该是：
- 多个 agent 角色对需求达成一致（自动判定）
- 用户可以随时对话质疑，agent 据此修订
- **没有"等人勾选"这个阻塞点**

**需要确认**：老师说的「没有人工介入」是否也覆盖这个六人确认？（Q1 的 a/d 子问题）
