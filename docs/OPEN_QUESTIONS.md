### Q1【最高优先】「圆桌交互」具体是什么形态？

**背景**

老师原话：

> 也包括**执行交互部分**，比如**圆桌交互**，这些都属于作业 3 需要考虑的内容

**现状**

当前没有任何"圆桌"形态的交互。现有的交互是：
- 讨论阶段：固定两处人工介入（价值裁决、六人确认）
- 编排阶段：推进一步 / 运行至完成

**我的理解**（待确认）

多 agent 与用户"围坐"，用户可以：
- 点名某个 agent 发言
- 追问某个观点
- 质疑并要求举证
- 让两个 agent 辩论

**为什么重要**

这是组 3 的核心工作（估 20h）。形态不定，无法开工。

**建议问法**
> 作业 3 提到的「圆桌交互」，是不是指多个 agent 和用户在同一界面里，用户可以点名某个 agent 发言、追问或质疑？
> 还是指 agent 之间就某个问题展开辩论、用户旁听并可插话？
> 这个交互发生在哪个阶段——讨论阶段、执行阶段，还是两者都有？

### Q2【高优先】案例项目选哪个？四则混合运算够不够？

**背景**

老师：

> 光设计流程有啥用，肯定要跑案例项目啊，通过案例优化流程，课上提了好多次了，比如**先跑通四则混合运算**

**现状**

仓库现有两个 fixture：校园失物招领（24 任务）、设备借用（11 任务）。这两个都是"业务系统"，比"四则混合运算"复杂得多。

**为什么重要**

案例决定"第一段打通链路"的目标。四则混合运算够简单，适合跑通；但它能否验证通用性存疑。

**建议问法**
> 「四则混合运算」是作为**跑通链路的第一个案例**，还是作为**主要的验收案例**？
> 如果是前者，我们跑通后是否要换更复杂的案例（如失物招领）来验证通用性？

### Q5 三个组如何并行改前端？

**现状**

`frontend/src/App.tsx` 约 1000 行，包含 8 个页面的全部逻辑。三组同时改必然冲突。

**方案**

| 做法 | 优点 | 缺点 |
|---|---|---|
| A. 拆分页面到独立文件 | 冲突面小，符合 React 常规 | 需一次重构（4—6h） |
| B. 按 `src/stages/stage1|2|3/` 分目录 | 边界清晰 | 与现有八页面结构不一致 |
| C. 不改，靠分支 + 频繁合并 | 零成本 | App.tsx 反复冲突 |

**建议**：A。这是三组并行改前端的前提。

**需要你决定**：是否接受这次重构？
