## 二、阶段 1 的流程设计

### 2.1 两种模式：完整 vs 简化

老师明确要求**向下兼容**：

> 这部分不一定直接讨论出设计规格，可以细化，可以先讨论出建设方案，转为需求规格（需要确认），再到设计规格（需要评审）
> 是否需要这么细**取决于项目类型和规模**
> 一般小项目才会靠一个会直接讨论出设计规格

```text
【完整模式】（中大型项目）
  需求 → 讨论 → 建设方案 → 需求规格 → 设计规格 → 交付
                              ↑            ↑
                          agent 自我确认  agent 自我评审

【简化模式】（小项目）
  需求 → 讨论 → 设计规格 → 交付

【极简模式】（微项目）
  需求 → 讨论 → 直接出结论
```

**关键修正**：原图中的「需求规格(**确认**)」「设计规格(**评审**)」如果理解成人工审批，就与「没有人工介入」矛盾。正确理解是：

| 环节 | 谁来做 | 用户角色 |
|---|---|---|
| 需求规格确认 | **agent 之间互相确认** | 可通过对话提出异议 |
| 设计规格评审 | **agent 之间互相评审** | 可通过对话提出异议 |

**设计要点**：这三种模式不是三套代码，是**同一个状态机的不同裁剪**。状态机要支持"跳过某些阶段"。

### 2.2 八个阶段的职责

| 阶段 | 代号 | 职责 | 产出 | 用户交互 | 阻塞？ |
|---|---|---|---|---|---|
| 框定 | A | 澄清需求、列隐含假设、提开放问题 | 问题定义、假设清单 | 可对话追问 | ❌ 不阻塞 |
| 独立发散 | B | 四角色互不可见地出观点 | 观点列表（claims） | 旁听 | ❌ |
| 聚类整合 | C | 归并去重，形成候选方向 | 聚类（clusters） | 旁听 | ❌ |
| 结构化批判 | D | 角色间互评，质疑者攻击 | 异议（objections） | 可插话质疑 | ❌ |
| 共识评价 | E | agent 打分；有分歧则 **agent 自动辩论** | 评价结果 | 可插话表态 | ❌ |
| 方案审阅 | F | 起草 Proposal，**agent 互相 sign-off** | Proposal 草案 | 可插话 | ❌ |
| 需求确认 | G | **agent 互相确认**，发布 R1 | 需求规格 R1 | 可插话 | ❌ |
| 设计规格 | H | 细化接口、错误码、字段边界、数据模型 | 设计规格 | 可插话 | ❌ |

**核心原则**：**没有任何阶段会因为等用户而停下**。用户的所有输入都是「随时可插话」，不是「必须回答才能继续」。

### 2.3 当前实现的差距

现有 B02 讨论状态机是 A—H，但：

| 差距 | 说明 | 严重度 |
|---|---|---|
| **3 处 `WAITING_HUMAN` 审批门** | 与「没有人工介入」直接冲突 | **P0** |
| A 阶段无用户问答 | 「框定」只生成假设，不问用户 | P1 |
| 无「随时插话」通道 | 用户只能通过固定 API 触发，不能自由对话 | **P0** |
| H 不存在 | 现状态机 H 是 COMPLETED（结束），不是「设计规格」 | **P0** |
| 无简化模式 | 必须走完整八阶段 | P1 |
| 六人确认是人工勾选 | 应改为 agent 互相确认 | **P0** |

**三处审批门的具体位置**（`b02-workflow-agent/backend/controller.py`）：

| 行号 | 触发 | 现有行为 | 改为 |
|---|---|---|---|
| `:170` | EVALUATE 有高影响分歧 | `WAITING_HUMAN` 等人裁决 | agent 自动辩论 → 自动判定 |
| `:195` | PROPOSAL_REVIEW 被拒 | `WAITING_HUMAN` 等人决定 | 自动修订重试（有限轮次） |
| `:208` | HUMAN_CONFIRMATION | 等六人勾选 | agent 互相确认 |

**结论**：需要（a）改造 3 处审批门为自动；（b）新增「随时插话」通道；（c）把 H 重新定义为「设计规格产出」；（d）加入跳阶段能力。

### 2.3.1 「六人确认」的改造方案（用户已明确：唯一的人只有用户）

用户原话：

> 「没有人工介入」覆盖六人确认，**唯一的人只有用户**。

**现状的问题**

| 现有 | 问题 |
|---|---|
| `MEMBERS = ("成员 A", ..., "成员 F")` 六个人类成员名 | 人类身份，与"无人工介入"冲突 |
| `publish()` 要求 `set(members) == set(MEMBERS)` | 必须六人全勾选才发 R1 |
| 前端是六个 check box | 表单式审批 UI |

**改造方案**

```text
现有：                         改为：
                                
六名人类勾选                    多个 agent 角色各自表态
      ↓                              ↓
凑齐 6 个才发 R1                 达成共识（如 4/4 agree）即发 R1
      ↓                              ↓
R1 发布                          R1 发布
                                
                                + 用户可随时对话质疑
                                + 用户质疑可触发重新表态
```

**具体实现建议**

| 层 | 改动 |
|---|---|
| 数据 | `MEMBERS` 从人类名改为 **agent 角色 ID**（如 `PM-01`, `ARCH-01`, `USER-01`, `DEVIL-01`） |
| 判定 | `publish()` 从「六人全部勾选」改为「所有 agent 角色 agree 或 unconditionally agree」 |
| 前端 | 六个 check box → **agent 表态卡片**（显示每个角色的 stance 与理由） |
| 用户 | 增加一个**对话输入框**，用户可提出质疑；质疑会触发相关 agent 重新表态 |

**保留的语义**

- 仍然要求**多角色**（不是单个 agent 说了算）
- 仍然有「异议必须被解决」的门槛
- 但**判定者是 agent，不是人**

**关键代码位置**：`b02-workflow-agent/backend/adapters.py` 的 `publish()` 方法。

### 2.3.2 用户交互的并行式实现（Q1a：选简单的）

用户答复「打断和并行都行，选一个实现较为简单的」。选择**并行式**。

**机制**

```text
任意时刻：
   用户发消息
        ↓
   写入 conversation_messages 表（consumed_at = NULL）
        ↓
   [不阻塞] 当前阶段继续跑
        ↓
   阶段边界检查：有未消费的用户消息吗？
        ↓ 有
   agent 读取消息，应用到当前产物
        ↓
   标记 consumed_at，记录 applied_to
        ↓
   继续下一阶段
```

**为什么这是最简单可行的方案**

| 优点 | 说明 |
|---|---|
| 不需要中断正在执行的 agent | 避免状态恢复的复杂性 |
| 复用现有阶段边界 | B02 状态机本来就在阶段间有检查点 |
| 天然符合「无人工介入」 | 流程永远不会因为等用户而停 |
| 用户输入可追溯 | `consumed_at` / `applied_to` 记录了影响链 |

**风险与缓解**

| 风险 | 缓解 |
|---|---|
| 用户觉得"说了没反应" | 前端显示「已收到，将在当前阶段结束后应用」 |
| 用户连续发多条 | 按时间排序，一次性全部消费 |
| 用户消息与 agent 结论冲突 | agent 需显式回应："已考虑你的意见，但..." |

### 2.3.3 对话记忆的表设计（Q1d）

用户明确「可采用 SQL 记忆」。建议放在 B03 的 SQLite（复用现有 `TaskStateStore` 的连接管理）。

```sql
CREATE TABLE IF NOT EXISTS conversation_messages (
    message_id   TEXT PRIMARY KEY,
    run_id       TEXT NOT NULL,
    stage        TEXT,              -- 产生/消费时的阶段 A—H
    role         TEXT NOT NULL,     -- 'user' | 'agent:<role_id>' | 'system'
    content      TEXT NOT NULL,
    created_at   TEXT NOT NULL,
    consumed_at  TEXT,              -- agent 消费时间；NULL = 待消费
    applied_to   TEXT               -- 应用到了哪个产物版本
);
CREATE INDEX IF NOT EXISTS idx_conv_run ON conversation_messages(run_id, created_at);
CREATE INDEX IF NOT EXISTS idx_conv_pending ON conversation_messages(run_id, consumed_at);
```

**与现有表的关系**

| 表 | 记录什么 | 区别 |
|---|---|---|
| `conversation_messages` | **用户/agent 的对话内容** | 输入，可能被消费也可能不被消费 |
| `task_run_events` | **状态变化事件** | 已发生的事实，不可变更 |

两者独立：对话不是状态变化，状态变化会引用对话（通过 `applied_to`）。

### 2.4 讨论长度控制

老师明确：

> 多智能体群体会议讨论**不适宜讨论过长**，容易挤爆智能体的上下文又引起不必要的幻觉
> 所以**分段**是个很有效的方式

**设计约束**：

| 约束 | 具体做法 |
|---|---|
| 单轮讨论有上限 | `max_rounds` 硬限制（现有参数，默认 2） |
| 每段有收敛条件 | 阶段间检查，不满足不前进 |
| 上下文不累积 | 用黑板 + 每轮摘要，不传完整历史（现有做法） |
| 阶段间可暂停 | 避免一次性跑完 |

## 三、阶段 2 的流程设计

### 3.1 主流程

```text
设计规格
   ↓
[B01] 任务分解
   ├─ 按需求条目推导任务
   ├─ 建立依赖关系
   └─ 生成 DAG
   ↓
[用户编辑]  ←──── 关键：可增删任务、改依赖、改验收条件
   ↓
[校验] 依赖存在、无环、需求覆盖、产物唯一
   ↓
[编排] 计算拓扑序与并行批次
   ↓
[B02] 逐层派发
   ├─ 依赖就绪 → READY
   ├─ 派发 → RUNNING
   └─ 提交 → REVIEWING
   ↓
[B04] 执行
   ↓
[B06] 验收
   ├─ 通过 → SUCCEEDED
   ├─ 失败 → 重试（有限）
   └─ 阻断 → BLOCKED + 下游传播
   ↓
完成 / 阻断
```

### 3.2 用户编辑节点关系（核心需求）

老师三次强调：

> 用户能随时进行交互（**编辑各节点关系**等）

**当前实现的问题**（代码级）：

```tsx
// frontend/src/components/TaskGraph.tsx
const [nodes, setNodes, onNodesChange] = useNodesState(layoutedNodes);
useEffect(() => {
  setNodes(layoutedNodes.map(...));   // ← 每次 tasks 变化就覆盖
  setEdges(layoutedEdges);
}, [layoutedNodes, layoutedEdges, ...]);
```

虽然有 `onNodesChange` / `onEdgesChange`，但：
1. 每次都从 `layoutTasks(tasks)` 重新布局，**用户的拖动会被覆盖**
2. 编辑**不会回写到后端**（没有 API）
3. 没有"增删任务"的入口

**要做的**：

| # | 能力 | 说明 |
|---|---|---|
| a | 拖动节点保存位置 | 布局与数据分离，位置存在前端或后端 |
| b | 增删任务 | 表单创建新任务 / 删除任务 |
| c | 改依赖关系 | 连线 / 断线，写回后端并重新校验 |
| d | 改验收条件/测试编号 | 编辑任务字段 |
| e | 编辑后重新校验 | 依赖存在、无环、需求覆盖 |
| f | 编辑写回后端 | 新增 API：`PATCH /api/task-plans/{plan_id}/tasks/{task_id}` |

**注意**：编辑必须走"生成新 plan_version"的路径，不能原地改已派发的计划（现有 `register_plan` 有版本冲突保护，是正确设计）。

### 3.3 推到执行（核心需求）

老师：

> **不止编排，还要推到执行**

第二轮追问「执行指完成用户所需软件吗」，老师回答：

> **产出用户所需软件。**

**第三轮进一步收敛边界**：

> 技术栈按你推荐的来。**不用真的制作软件，制作一个网页端即可。暂时不用。**

**准确的目标**

| 项 | 结论 |
|---|---|
| 产物形态 | **网页端应用**（纯静态 HTML/CSS/JS 起步） |
| 是否真的部署 | **否**（"暂时不用"） |
| 验收方式 | 浏览器能打开、核心功能可用 |

**当前实现**：

```python
# b02-workflow-agent/backend/task_api.py
def default_stack(db_path, *, execution_mode: str = "mock", ...):
    gateway = TaskExecutionGateway(mode=execution_mode, scenario=scenario)
```

默认 `mock`，执行结果标注 `simulated=True`。**不满足要求**。

**要做的**：

| # | 能力 | 说明 | 估时 |
|---|---|---|---|
| a | 接真实 runner | `runner_callable` 实现，B04 envelope 转换 | 8h |
| b | **产出网页文件** | Agent 写 HTML/CSS/JS，落到 `work/deliverables/<run_id>/` | 8h |
| c | 网页预览 | B02 静态托管 `/preview/<run_id>/`，复用 7100 端口 | 4h |
| d | 不做 | 自动测试、自动部署、后端服务 | — |

**合计约 20h**（比原估 28h 少，因为明确不需要真实软件工程）。

**建议的技术栈**（最少依赖、最易验证）

```text
产物：单个 index.html（内联 CSS/JS）
预览：B02 的 static server 加一个 /preview/<run_id>/ 路由
验证：人工打开浏览器点几下
```

### 3.4 案例策略：先通用框架，再用案例测试

老师第二轮明确：

> **不要针对某个具体的案例**，先做通用框架，再用各个案例进行测试优化。

### 3.4.1 ⚠️ 现有案例都不完整（用户重要提示）

用户指出：

> 当前生成出的案例**并没有经过与用户的交互，也没有经过多智能体讨论**，这些案例是**不完整的**，校园失物目前大概只能到 **L2**。

**代码级核实**：

| 文件 | 有无 `phase1_source` | 结论 |
|---|---|---|
| `campus-lost-found.spec.json` | ❌ 无 | 手写，未经讨论 |
| `campus-lost-found.plan.json` | ❌ 无 | 手写规格推导 |
| `lab-equipment-loan.spec.md` | ❌ 无 | 手写 |

真正的讨论产物会带 `phase1_source`：

```python
"phase1_source": {
    "run_id": "...", "r1_version": "R1",
    "generation_source": "llm", "confirmed_by": [...]
}
```

**结论**：现有 fixture 只能做**阶段 2 的输入测试**，不能作为端到端案例的证明。

### 3.4.2 案例成熟度分级

| 级别 | 定义 | 判定标准 | 现有 |
|---|---|---|---|
| **C0** | 手写规格 | 有 spec，无 `phase1_source` | ✅ campus、lab |
| **C1** | 单块可用 | 能驱动阶段 2 分解编排 | ⚠️ 部分 |
| **C2** | 讨论产出 | 有多智能体讨论 + `phase1_source` | ❌ 无 |
| **C3** | 端到端完整 | C2 + 真实执行 + 可运行网页 | ❌ 无 |

**目标**：至少一个 C3 案例。

### 3.4.3 案例分层与来源

| 层级 | 案例 | 来源 | 预期成熟度 |
|---|---|---|---|
| L1 | 四则混合运算计算器 | 手写规格（最快验证链路） | 跑通后可达 C3 |
| L2 | 待办事项 / 计数器 | 手写规格 | C3 |
| L3 | 设备借用系统 | 现有 fixture（11 任务） | C0 → 需重跑 |
| L4 | 校园失物招领 | 现有 fixture（24 任务，但只有 5 条需求） | **实际仅 C0，用户说"只到 L2 水平"** |

> **修正**：此前把校园失物招领当作 L4 复杂案例是错的。它只有 5 条需求，规模上不算复杂，且未经讨论，实际只能算 L2 水平的手写样例。

**迭代流程**：

```text
通用框架（领域无关）
   ↓
跑 L1 案例 → 发现问题 → 修框架
   ↓
跑 L2 案例 → 发现问题 → 修框架
   ↓
用完整流程生成 L3/L4 案例（此时才可信）
```

**真正的目标不是"跑通某个案例"，而是"用流程自己生成案例"**。现有手写 fixture 只是阶段 2 的测试输入，不是最终交付物。
   ↓
再跑一次，对比
```

**这意味着**：需要一个**可重复的案例集**，且每次改动后能自动重跑对比。

## 四、阶段 3 的流程设计

### 4.1 三大块

老师：

### 4.2 观测数据的设计（老师点名）

**现状**：已有事件流（12 种 `TASK_*` 事件）、任务状态、尝试历史、耗时。

**缺的是**：

| # | 缺什么 | 说明 |
|---|---|---|
| a | 讨论阶段的观测 | 现在只有任务编排阶段的事件，讨论阶段的事件（`IDEA_FRAMED` 等）没有统一进观测体系 |
| b | Agent 层面的观测 | 每个 agent 的输入、输出、token 用量、耗时 |
| c | 观测数据的 schema | 没有明确定义"什么算观测数据" |
| d | 跨阶段时间轴 | 讨论与编排的时间轴是分开的 |

**建议的观测数据模型**：

```text
Observation
├── 主体：run / stage / task / agent / model_call
├── 类型：state_change / input / output / error / metric
├── 时间：started_at / finished_at / duration
├── 上下文：plan_version / input_snapshot / attempt_id
└── 载荷：结构化 payload + 关联引用
```

### 4.3 圆桌交互（老师点名）

**我的理解**（待确认）：多个 agent 与用户围坐，用户可以：

- 点名某个 agent 发言
- 追问某个观点
- 质疑并要求举证
- 让两个 agent 辩论

**与阶段 1 讨论的区别**：

| 阶段 1 的讨论 | 阶段 3 的圆桌交互 |
|---|---|
| 流程驱动（按 A—H 走） | 用户驱动（随时插入） |
| 预设角色发言顺序 | 用户点名 |
| 目标是收敛 | 目标是澄清 |

**这可能意味着阶段 1 的讨论机制要改造**，使其支持"随时插入的圆桌模式"。这是需要与老师确认的点。

### 4.4 事后回溯

老师原话是「进一步也可以考虑事后回溯等」，优先级较低。

**当前已有**：技术级 `replay`（事件重放比对）、`restore`（断点恢复）。

**缺的**：业务级复盘——耗时排名、重试热点、缺陷来源、不同运行的对比。

## 七、实施策略：先跑通再迭代

老师：

> 不用太急，多想想，**先跑通再迭代优化**
> 我们后续肯定都是通过**跑项目案例，迭代优化流程**

### 7.1 建议的实施顺序

```text
第 0 步：搭通用框架骨架（不绑定案例）
   ↓
第 1 步：打通一条最简链路（用 L1 案例验证）
   需求 → 讨论（简化）→ 设计规格 → 分解 → 编排 → 执行（真实）→ 产出软件
   ↓
第 2 步：让这条链路可重复
   固定输入，可自动重跑，有对比
   ↓
第 3 步：逐步加能力
   加用户交互 → 加编辑 → 加观测 → 加圆桌
   ↓
第 4 步：换更复杂的案例（L2 → L3 → L4）验证通用性
```

**注意第 0 步**：老师明确「不要针对某个具体的案例，先做通用框架」。所以不是"选一个案例然后为它定制"，而是"搭通用骨架，再用案例检验"。

### 7.2 为什么不能按模块并行开工

如果三个组各自开工：
- 组 1 做完讨论，发现阶段 2 消费不了设计规格
- 组 2 做完编排，发现执行是 mock
- 组 3 做完观测框架，发现前两步都没产出可观测的数据

**老师说的「空对空」正是这个风险**。

### 7.3 与三组分工的关系

三组分工仍然成立，但**第一段（第 0—2 步）建议全员共同完成**，打通链路后再分组并行扩展。

详见 `TEAM_DIVISION.md`。
