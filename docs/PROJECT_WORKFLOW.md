## 二、阶段 1 的流程设计

### 2.1 两种模式：完整 vs 简化

老师明确要求**向下兼容**：

> 这部分不一定直接讨论出设计规格，可以细化，可以先讨论出建设方案，转为需求规格（需要确认），再到设计规格（需要评审）
> 是否需要这么细**取决于项目类型和规模**
> 一般小项目才会靠一个会直接讨论出设计规格

```text
【完整模式】（中大型项目）
  需求 → 讨论 → 建设方案 → 需求规格 → 设计规格 → 交付
                              ↑            ↑
                          agent 自我确认  agent 自我评审

【简化模式】（小项目）
  需求 → 讨论 → 设计规格 → 交付

【极简模式】（微项目）
  需求 → 讨论 → 直接出结论
```

**关键修正**：原图中的「需求规格(**确认**)」「设计规格(**评审**)」如果理解成人工审批，就与「没有人工介入」矛盾。正确理解是：

| 环节 | 谁来做 | 用户角色 |
|---|---|---|
| 需求规格确认 | **agent 之间互相确认** | 可通过对话提出异议 |
| 设计规格评审 | **agent 之间互相评审** | 可通过对话提出异议 |

**设计要点**：这三种模式不是三套代码，是**同一个状态机的不同裁剪**。状态机要支持"跳过某些阶段"。

### 2.2 八个阶段的职责

| 阶段 | 代号 | 职责 | 产出 | 用户交互 | 阻塞？ |
|---|---|---|---|---|---|
| 框定 | A | 澄清需求、列隐含假设、提开放问题 | 问题定义、假设清单 | 可对话追问 | ❌ 不阻塞 |
| 独立发散 | B | 四角色互不可见地出观点 | 观点列表（claims） | 旁听 | ❌ |
| 聚类整合 | C | 归并去重，形成候选方向 | 聚类（clusters） | 旁听 | ❌ |
| 结构化批判 | D | 角色间互评，质疑者攻击 | 异议（objections） | 可插话质疑 | ❌ |
| 共识评价 | E | agent 打分；有分歧则 **agent 自动辩论** | 评价结果 | 可插话表态 | ❌ |
| 方案审阅 | F | 起草 Proposal，**agent 互相 sign-off** | Proposal 草案 | 可插话 | ❌ |
| 需求确认 | G | **agent 互相确认**，发布 R1 | 需求规格 R1 | 可插话 | ❌ |
| 设计规格 | H | 细化接口、错误码、字段边界、数据模型 | 设计规格 | 可插话 | ❌ |

**核心原则**：**没有任何阶段会因为等用户而停下**。用户的所有输入都是「随时可插话」，不是「必须回答才能继续」。

### 2.3 当前实现的差距

现有 B02 讨论状态机是 A—H，但：

| 差距 | 说明 | 严重度 |
|---|---|---|
| **3 处 `WAITING_HUMAN` 审批门** | 与「没有人工介入」直接冲突 | **P0** |
| A 阶段无用户问答 | 「框定」只生成假设，不问用户 | P1 |
| 无「随时插话」通道 | 用户只能通过固定 API 触发，不能自由对话 | **P0** |
| H 不存在 | 现状态机 H 是 COMPLETED（结束），不是「设计规格」 | **P0** |
| 无简化模式 | 必须走完整八阶段 | P1 |
| 六人确认是人工勾选 | 应改为 agent 互相确认 | **P0** |

**三处审批门的具体位置**（`b02-workflow-agent/backend/controller.py`）：

| 行号 | 触发 | 现有行为 | 改为 |
|---|---|---|---|
| `:170` | EVALUATE 有高影响分歧 | `WAITING_HUMAN` 等人裁决 | agent 自动辩论 → 自动判定 |
| `:195` | PROPOSAL_REVIEW 被拒 | `WAITING_HUMAN` 等人决定 | 自动修订重试（有限轮次） |
| `:208` | HUMAN_CONFIRMATION | 等六人勾选 | agent 互相确认 |

**结论**：需要（a）改造 3 处审批门为自动；（b）新增「随时插话」通道；（c）把 H 重新定义为「设计规格产出」；（d）加入跳阶段能力。

### 2.4 讨论长度控制

老师明确：

> 多智能体群体会议讨论**不适宜讨论过长**，容易挤爆智能体的上下文又引起不必要的幻觉
> 所以**分段**是个很有效的方式

**设计约束**：

| 约束 | 具体做法 |
|---|---|
| 单轮讨论有上限 | `max_rounds` 硬限制（现有参数，默认 2） |
| 每段有收敛条件 | 阶段间检查，不满足不前进 |
| 上下文不累积 | 用黑板 + 每轮摘要，不传完整历史（现有做法） |
| 阶段间可暂停 | 避免一次性跑完 |

## 三、阶段 2 的流程设计

### 3.1 主流程

```text
设计规格
   ↓
[B01] 任务分解
   ├─ 按需求条目推导任务
   ├─ 建立依赖关系
   └─ 生成 DAG
   ↓
[用户编辑]  ←──── 关键：可增删任务、改依赖、改验收条件
   ↓
[校验] 依赖存在、无环、需求覆盖、产物唯一
   ↓
[编排] 计算拓扑序与并行批次
   ↓
[B02] 逐层派发
   ├─ 依赖就绪 → READY
   ├─ 派发 → RUNNING
   └─ 提交 → REVIEWING
   ↓
[B04] 执行
   ↓
[B06] 验收
   ├─ 通过 → SUCCEEDED
   ├─ 失败 → 重试（有限）
   └─ 阻断 → BLOCKED + 下游传播
   ↓
完成 / 阻断
```

### 3.2 用户编辑节点关系（核心需求）

老师三次强调：

> 用户能随时进行交互（**编辑各节点关系**等）

**当前实现的问题**（代码级）：

```tsx
// frontend/src/components/TaskGraph.tsx
const [nodes, setNodes, onNodesChange] = useNodesState(layoutedNodes);
useEffect(() => {
  setNodes(layoutedNodes.map(...));   // ← 每次 tasks 变化就覆盖
  setEdges(layoutedEdges);
}, [layoutedNodes, layoutedEdges, ...]);
```

虽然有 `onNodesChange` / `onEdgesChange`，但：
1. 每次都从 `layoutTasks(tasks)` 重新布局，**用户的拖动会被覆盖**
2. 编辑**不会回写到后端**（没有 API）
3. 没有"增删任务"的入口

**要做的**：

| # | 能力 | 说明 |
|---|---|---|
| a | 拖动节点保存位置 | 布局与数据分离，位置存在前端或后端 |
| b | 增删任务 | 表单创建新任务 / 删除任务 |
| c | 改依赖关系 | 连线 / 断线，写回后端并重新校验 |
| d | 改验收条件/测试编号 | 编辑任务字段 |
| e | 编辑后重新校验 | 依赖存在、无环、需求覆盖 |
| f | 编辑写回后端 | 新增 API：`PATCH /api/task-plans/{plan_id}/tasks/{task_id}` |

**注意**：编辑必须走"生成新 plan_version"的路径，不能原地改已派发的计划（现有 `register_plan` 有版本冲突保护，是正确设计）。

### 3.3 推到执行（核心需求）

老师：

> **不止编排，还要推到执行**

第二轮追问「执行指完成用户所需软件吗」，老师回答：

> **产出用户所需软件。**

这不是文档、不是伪代码、不是 mock —— 是**能跑起来的软件**。

**当前实现**：

```python
# b02-workflow-agent/backend/task_api.py
def default_stack(db_path, *, execution_mode: str = "mock", ...):
    gateway = TaskExecutionGateway(mode=execution_mode, scenario=scenario)
```

默认 `mock`，执行结果标注 `simulated=True`。**不满足"产出用户所需软件"**。

**要做的**：

| # | 能力 | 说明 |
|---|---|---|
| a | 接真实 runner | `runner_callable` 实现，B04 envelope 转换 |
| b | 真实产出代码 | 让 Agent 真的写可运行代码 |
| c | 真实跑测试 | B06 的受控测试执行 |
| d | 交付可运行软件 | 用户拿到能跑的程序 |

**待明确的技术边界**（可在实施中确定）：支持哪些技术栈、在哪运行、如何验证。

### 3.4 案例策略：先通用框架，再用案例测试

老师第二轮明确：

> **不要针对某个具体的案例**，先做通用框架，再用各个案例进行测试优化。

**这修正了此前的理解**：

| 之前以为 | 实际要求 |
|---|---|
| 四则混合运算是项目目标 | ❌ 它只是**测试用例之一** |
| 针对某案例优化 | ❌ 框架必须领域无关 |
| — | ✅ **框架先行，案例验证** |

**通用性的现成证据**：同一套 B01 动态计划，从 campus 规格生成 24 任务、从 lab 规格生成 11 任务，**任务数由规格推导**，不是写死。

**建议的案例分层**（用于验证通用性）：

| 层级 | 案例 | 验证什么 | 规模 |
|---|---|---|---|
| L1 | 四则混合运算计算器 | 链路能通 | 3—5 任务 |
| L2 | 待办事项 / 计数器 | 基础 CRUD | 8—12 任务 |
| L3 | 设备借用系统 | 多模块协作 | 11 任务（已有 fixture） |
| L4 | 校园失物招领 | 大规模编排 | 24 任务（已有 fixture） |

**迭代流程**：

```text
通用框架（领域无关）
   ↓
跑 L1 案例 → 发现问题 → 修框架
   ↓
跑 L2 案例 → 发现问题 → 修框架
   ↓
跑 L3/L4 → 验证通用性
```
   ↓
再跑一次，对比
```

**这意味着**：需要一个**可重复的案例集**，且每次改动后能自动重跑对比。

## 四、阶段 3 的流程设计

### 4.1 三大块

老师：

> 除了 1、2 的可视化部分，主要是**设计和实现执行过程中哪些数据需要记录、怎么展示**，也包括**执行交互部分**，比如**圆桌交互**

```text
阶段 3
├── A. 收编 1、2 的可视化
│     └─ 统一框架，不是重做
│
├── B. 观测数据
│     ├─ 定义：哪些数据要记录（schema）
│     └─ 展示：怎么呈现
│
└── C. 执行交互
      ├── 圆桌交互（多 agent + 用户同场）
      └── **非阻塞**：用户不响应时流程继续
```

### 4.2 观测数据的设计（老师点名）

**现状**：已有事件流（12 种 `TASK_*` 事件）、任务状态、尝试历史、耗时。

**缺的是**：

| # | 缺什么 | 说明 |
|---|---|---|
| a | 讨论阶段的观测 | 现在只有任务编排阶段的事件，讨论阶段的事件（`IDEA_FRAMED` 等）没有统一进观测体系 |
| b | Agent 层面的观测 | 每个 agent 的输入、输出、token 用量、耗时 |
| c | 观测数据的 schema | 没有明确定义"什么算观测数据" |
| d | 跨阶段时间轴 | 讨论与编排的时间轴是分开的 |

**建议的观测数据模型**：

```text
Observation
├── 主体：run / stage / task / agent / model_call
├── 类型：state_change / input / output / error / metric
├── 时间：started_at / finished_at / duration
├── 上下文：plan_version / input_snapshot / attempt_id
└── 载荷：结构化 payload + 关联引用
```

### 4.3 圆桌交互（老师点名）

**我的理解**（待确认）：多个 agent 与用户围坐，用户可以：

- 点名某个 agent 发言
- 追问某个观点
- 质疑并要求举证
- 让两个 agent 辩论

**与阶段 1 讨论的区别**：

| 阶段 1 的讨论 | 阶段 3 的圆桌交互 |
|---|---|
| 流程驱动（按 A—H 走） | 用户驱动（随时插入） |
| 预设角色发言顺序 | 用户点名 |
| 目标是收敛 | 目标是澄清 |

**这可能意味着阶段 1 的讨论机制要改造**，使其支持"随时插入的圆桌模式"。这是需要与老师确认的点。

### 4.4 事后回溯

老师原话是「进一步也可以考虑事后回溯等」，优先级较低。

**当前已有**：技术级 `replay`（事件重放比对）、`restore`（断点恢复）。

**缺的**：业务级复盘——耗时排名、重试热点、缺陷来源、不同运行的对比。

## 七、实施策略：先跑通再迭代

老师：

> 不用太急，多想想，**先跑通再迭代优化**
> 我们后续肯定都是通过**跑项目案例，迭代优化流程**

### 7.1 建议的实施顺序

```text
第 0 步：搭通用框架骨架（不绑定案例）
   ↓
第 1 步：打通一条最简链路（用 L1 案例验证）
   需求 → 讨论（简化）→ 设计规格 → 分解 → 编排 → 执行（真实）→ 产出软件
   ↓
第 2 步：让这条链路可重复
   固定输入，可自动重跑，有对比
   ↓
第 3 步：逐步加能力
   加用户交互 → 加编辑 → 加观测 → 加圆桌
   ↓
第 4 步：换更复杂的案例（L2 → L3 → L4）验证通用性
```

**注意第 0 步**：老师明确「不要针对某个具体的案例，先做通用框架」。所以不是"选一个案例然后为它定制"，而是"搭通用骨架，再用案例检验"。

### 7.2 为什么不能按模块并行开工

如果三个组各自开工：
- 组 1 做完讨论，发现阶段 2 消费不了设计规格
- 组 2 做完编排，发现执行是 mock
- 组 3 做完观测框架，发现前两步都没产出可观测的数据

|---|---|---|
