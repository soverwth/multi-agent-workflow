## 一、任务目标

### 1.1 总目标

构建一个**通用、全自动化的多智能体软件工程（SE）Workflow 平台**：用户输入一个想法或需求，平台组织多个 agent 进行讨论并随时接受用户交互，产出尽可能细化的设计规格；再把设计规格分解为任务 DAG、可视化编排并**真实执行**，最终产出用户所需的网页端软件；同时把讨论、编排、执行的全过程变成可观测、可回溯的数据。

一句话链路：

```text
用户想法 → 多 agent 讨论（用户可随时插话）→ 设计规格
       → 任务分解 → 可视化编排 → 真实执行 → 独立验收 → 网页产物
       → 全过程可观测 / 可回溯
```

项目定位的四个关键词：

| 关键词 | 含义 | 对目标的约束 |
|---|---|---|
| 自动化 | 流程由系统驱动，编排器是核心，不是"展示图" | 状态推进必须由编排器完成，不靠人工点按钮 |
| 没有人工介入 | 全流程不设审批门，不因等人而暂停 | 参与讨论与决策的主体是 agent，人的角色只有"用户" |
| 通用 | 不绑定具体业务领域 | 先做通用框架，业务案例只作为测试 fixture |
| 多方 agent + 用户交互 | 多角色协作，用户随时对话但**不是审批** | 交互必须是非阻塞的，且是一等公民 |

其中「人工介入」与「用户交互」在目标上是相反的，必须在设计时严格区分：

| | 人工介入 | 用户与 agent 交互 |
|---|---|---|
| 流程是否暂停 | 是（等人操作） | 否（agent 继续，用户随时插话） |
| 用户做什么 | 审批、勾选、裁决 | 提需求、追问、质疑、补充 |
| 项目是否采用 | 不采用 | 核心机制 |

### 1.2 阶段目标

项目按三个递进的课堂作业展开，对应三个相互衔接的阶段。

| 阶段 | 名称 | 一句话目标 | 核心产出 |
|---|---|---|---|
| 阶段一 | 需求 → 设计规格 | 用户想法经多智能体讨论与多轮交互，收敛为**尽可能细化**的设计规格 | 设计规格（需求条目 + 设计条目 + 接口契约 + 数据模型） |
| 阶段二 | 设计规格 → 编排 → 执行 | 设计规格经任务分解与可编辑编排后**推到真实执行**，产出用户所需软件 | 任务 DAG（可编辑）+ 执行过程 + 网页端产物 |
| 阶段三 | 可观测性框架 | 收编前两阶段的可视化，定义并展示执行过程数据，提供执行交互与事后回溯 | 观测数据 schema + 观测视图 + 圆桌交互 + 复盘 |

**阶段一目标（P0）**

1. 用户以一句话想法即可输入需求，系统能够追问澄清。
2. 多角色独立讨论：有独立发散、有批判、有共识评价，不能是单模型自问自答。
3. 用户与 agent 实时交互，且**流程不因等待用户而暂停**。
4. 全程**无人工审批门**：需求确认与设计规格评审由 agent 之间相互确认与评审完成。
5. 产出**尽可能细化**的设计规格，必须包含接口定义、错误码、字段边界、响应结构、数据模型与非功能约束，而不只是需求列表。
6. 讨论过程可视化：能看到 agent 的思考过程、观点与异议的增删、评分结果，需求规格与设计规格可直接查看。
7. 支持分阶段收敛并**向下兼容**：小项目可一步直达设计规格，中大型项目可先出建设方案、再需求规格、再设计规格。
8. 阶段一的终点不是一份"文档"，而是一个**可被机器签收的基线**：R1 与设计规格都带版本号、内容哈希与父版本引用，下游按基线编号消费，而不是按文件路径消费。

**阶段二目标（P0）**

1. 消费阶段一产出的细化设计规格，同时也支持外部规格独立测试。
2. 支持**增量分解与重新分解**，任务数量与依赖由规格推导，而非写死。
3. 用户可随时交互编辑编排节点：增删任务、改依赖、改验收条件，且编辑结果要能写回并重新校验。
4. 生成可视化编排器：任务节点、依赖边、状态、耗时、并行批次、执行进度可见。
5. 任务图不只表达"先后"：**条件分支**（按上游结果选择路径）与**阶段检查点**（可恢复的物理锚点）是图的一等节点，而不是在代码里特判。
6. **不止编排，还要推到执行**：真实执行任务并产出用户所需的网页端应用，验收标准是浏览器能打开、核心功能可用。
7. 执行过程可视化：执行状态、进度、产物、证据可追踪。
8. 提供执行控制能力：暂停、继续、中止。
9. 计划的每次编辑都是**新版本**，并用"期望版本号 + 输入哈希"做并发控制：两个人（或人与 agent）同时编辑时，后提交者得到明确的冲突而不是静默覆盖。

**阶段三目标（P0）**

1. **收编**阶段一、阶段二的可视化，形成统一表达，不是重复重做。
2. **定义执行过程中记录哪些数据**（观测数据 schema）：主体、类型、时间、上下文、载荷。其中"主体"必须包括**每一次模型调用**——它和任务、阶段一样是一等被观测对象，带请求哈希、用量与耗时。
3. **定义这些数据怎么展示**：观测视图与跨阶段时间轴。
4. **执行交互**，典型形态是圆桌交互：多个 agent 与用户在同一界面协作，用户可点名发言、追问观点、质疑要举证、让两个 agent 辩论、补充需求。
5. 执行交互同样**不阻塞**：用户不响应时流程继续按推荐方案推进。
6. 事后回溯不只看"状态怎么变"，还要能回答"**这个结论是哪次模型调用、读的哪版输入产生的**"。

### 1.3 目标必须满足的硬约束

| 编号 | 约束 | 对目标的具体要求 |
|---|---|---|
| N1 | 讨论不宜过长 | 讨论必须分段，有轮次上限与收敛条件，防止上下文膨胀引发幻觉 |
| N2 | 流程向下兼容 | 同一套状态机支持"完整 / 简化 / 极简"三种裁剪，可跳过部分阶段 |
| N3 | 通过跑案例迭代优化 | 目标实现必须可被可重复的案例集验证，不能"空对空" |
| N4 | 通用性 | 不针对具体案例定制，换规格即换项目 |
| N5 | 三个阶段的全程可观测 | 讨论、编排、执行都要能看到过程 |
| N6 | 全自动化、无人工介入 | 不设审批门，流程不自阻塞 |
| N7 | 单端口单网页 | 只用 7100 端口，单一 SPA 内路由，所有功能在同一网页内 |
| N8 | 模拟与真实不得互相冒充 | 模拟产物不得进入真实链路；真实模型缺失时显式报错，不静默回落到模拟 |

N7 的附加含义：阶段三新增的圆桌交互与观测视图**不能起新服务、新端口**，必须是现有工作台的一部分。

N8 的附加含义：演示基线只能用于演练，不得作为真实运行的输入；真实执行需要模型而未配置时，运行必须以明确错误结束，而不是用模拟结果"跑通"。

### 1.4 目标边界（明确不做）

| 不做的事 | 理由 |
|---|---|
| 云部署、多租户、计费 | 课程项目范围外 |
| 实时多人协同编辑 | 同上 |
| 通用聊天机器人 | 定位是 SE workflow，不是聊天工具 |
| 强制使用某个特定多智能体框架 | 该框架只是"可采用"的推荐方式 |
| 真实部署上线与生产级软件工程 | 产物形态收敛为"网页端可用"，暂不部署 |

### 1.5 目标的验收口径

**分阶段 P0 验收清单**

| 阶段 | 验收项 |
|---|---|
| 阶段一 | 需求输入与追问；多角色独立讨论；用户非阻塞实时交互；无人工审批门；细化的设计规格（含接口/错误码/字段边界/数据模型）；讨论过程可视化；分阶段收敛与向下兼容；R1 与设计规格为带哈希的基线 |
| 阶段二 | 消费细化基线；增量任务分解；用户可编辑节点关系；可视化编排器（含并行批次、条件分支、检查点）；计划版本 CAS 冲突可复现；真实执行并产出网页；执行过程可视化；执行控制 |
| 阶段三 | 收编前两阶段可视化；观测数据 schema（含模型调用）；观测数据展示；执行交互（圆桌）；事后回溯（含结论→模型调用的追溯） |

**三类证据分离口径**

"做完了"不能只有一种证据。借鉴 SE-lib 的做法，验收证据分三类，各自成文、互不替代：

| 证据类型 | 证明什么 | 产生方式 | 不能被什么替代 |
|---|---|---|---|
| 技术闭环 | 全链路可跑、契约一致、回放一致 | `verify_contracts.py` / `run_all_checks.py` / 四个演示场景 | 不能用模拟场景的通过替代真实模型 |
| 真实模型 | 真实 LLM 下规格、分解、产物质量可用 | 单独触发、记录模型 ID / 用量 / 耗时 / 输入哈希 | 不能默认触发产生费用；不能静默改用模拟 |
| 质量属性 | 性能、恢复、安全、可访问性达标 | 基准脚本（含前端大图帧率、断点恢复） | 不能只在文档里声明 |

**案例成熟度口径**

通用框架必须用案例验证，但案例本身也分成熟度，只有达到最高级别才能证明端到端可用：

| 级别 | 定义 | 判定标准 |
|---|---|---|
| C0 | 手写规格 | 有人工编写的 spec，但没有第一阶段的讨论来源 |
| C1 | 单块可用 | 能驱动阶段二的分解与编排，但不代表端到端 |
| C2 | 讨论产出 | 规格由多智能体讨论生成，带 `generation_source=llm` 的基线对象，R1 已确认发布 |
| C3 | 端到端完整 | 在 C2 基础上叠加真实执行产物与可运行网页 |

目标要求：**至少有一个 C3 案例**。手写 fixture 只能作为阶段二的输入测试，不能充当端到端案例的证据。

**通用性口径**

同一套流程、同一套编排器，更换规格就应产出不同规模的任务图（例如同一实现下，一个规格分解出 24 个任务、另一个规格分解出 11 个任务），任务数量必须由规格推导而非写死。

## 二、任务过程

### 2.1 总体过程

整个过程由三阶段串联，每一段都有明确输入、动作与产出，段与段之间靠**结构化产物**衔接而不是靠人。

```text
【阶段一】用户需求
    → 多智能体讨论（A—H 八阶段，用户随时插话、不阻塞）
    → 设计规格基线（需求条目 + 设计条目 + 接口契约 + 数据模型 + 哈希与父链）
              ↓ 设计规格基线（baseline_id + sha256）
【阶段二】任务分解 → 计划校验 → 可视化编排（可编辑）→ 调度派发
    → 受控执行 → 独立验收 → 重试/阻断 → 网页端产物
    （用户随时编辑节点，不阻塞）
              ↓ 编排过程 + 执行过程数据
【阶段三】收编可视化 + 观测数据 schema + 观测展示 + 圆桌交互 + 事后回溯
```

过程的三个基本特征：

1. **状态机驱动**：每一段都由显式状态与合法迁移控制，任何跳步都会被拒绝。
2. **黑板记录**：需求、设计、任务、观点、异议、决策、产物、证据都落在共享黑板上，过程可追溯。
3. **证据验收**：产物是否合格由独立的质量门按证据判定，不采信模型的自然语言声明。

### 2.2 阶段一过程：用户想法 → 设计规格

#### 2.2.1 八阶段主流程

| 阶段 | 代号 | 职责 | 产出 | 用户交互 | 是否阻塞 |
|---|---|---|---|---|---|
| 框定 | A | 澄清需求、列隐含假设、提开放问题 | 问题定义、假设清单 | 可对话追问 | 否 |
| 独立发散 | B | 多角色互不可见地各自出观点 | 观点列表 | 旁听 | 否 |
| 聚类整合 | C | 归并去重，形成候选方向 | 聚类结果 | 旁听 | 否 |
| 结构化批判 | D | 角色间赞同/反对/有条件赞同，质疑者发起攻击 | 异议列表 | 可插话质疑 | 否 |
| 共识评价 | E | agent 打分；有分歧则 agent 自动辩论后判定 | 评价结果 | 可插话表态 | 否 |
| 方案审阅 | F | 起草建设方案，agent 之间互相 sign-off | 方案草案 | 可插话 | 否 |
| 需求确认 | G | agent 之间互相确认后发布 R1 | 需求规格 R1 | 可插话 | 否 |
| 设计规格 | H | 细化接口、错误码、字段边界、数据模型 | 设计规格 | 可插话 | 否 |

过程原则：**没有任何阶段会因为等待用户而停下**。用户的所有输入都是"随时可插话"，不是"必须回答才能继续"。

过程要求中的两条关键规定：

- **不设审批门**：分歧不交给人类裁决，由 agent 自动辩论并判定；方案被拒不交给人决定，由 agent 自动修订重试（有限轮次）；需求确认不是人工勾选，而是 agent 角色各自表态后达成共识即发布 R1。
- **多角色始终保留**：即使判定者从人换成 agent，"多角色参与"的形式与"异议必须被解决"的门槛仍然保留。

#### 2.2.2 用户交互过程（并行式）

用户交互选择实现更简单、且与"无人工介入"天然一致的并行式：

```text
任意时刻：用户发消息
   ↓
写入对话记忆表（标记为未消费）
   ↓
不阻塞，当前阶段继续跑
   ↓
阶段边界检查：是否有未消费的用户消息
   ↓
有 → agent 读取并应用到当前产物
   ↓
标记消费时间，记录该输入影响了哪个产物版本
   ↓
继续下一阶段
```

过程需要一张对话记忆表承载这件事，字段至少包括：消息编号、所属运行、产生阶段、角色（用户 / 某 agent / 系统）、内容、创建时间、消费时间、应用到哪个产物版本。

该过程的语义边界：

| 场景 | 过程行为 |
|---|---|
| 用户长时间不回应 | 继续按推荐方案推进，不进入等待 |
| 用户连续发多条 | 按时间排序，在阶段边界一次性全部消费 |
| 用户意见与 agent 结论冲突 | agent 必须显式回应"已考虑你的意见，但……"，不能静默忽略 |
| 用户修改 agent 产出 | 允许修改，写回时保留版本记录 |
| 交互历史 | 需要持久化，与状态事件分开存储：对话是"输入"，事件是"状态变化" |

#### 2.2.3 分阶段收敛过程

同一套状态机按项目规模裁剪，向下兼容：

```text
完整模式（中大型）：需求 → 讨论 → 建设方案 → 需求规格 → 设计规格 → 阶段二
简化模式（小项目）：需求 → 讨论 → 设计规格 → 阶段二
极简模式（微项目）：需求 → 讨论 → 直接出结论
```

关键点：需求规格的"确认"与设计规格的"评审"都由 **agent 之间**完成，用户只能通过对话提出异议，不参与勾选式审批。

#### 2.2.4 设计规格细化过程

阶段一的终点必须是"设计级"规格，而不只是"需求级"列表。细化过程要覆盖以下部分：

| 部分 | 内容要求 |
|---|---|
| 需求条目 | 需求编号、标题、描述、优先级、验收条件、约束 |
| 接口定义 | 操作名称、方法、路径、鉴权、请求字段、响应字段、状态码 |
| 错误码 | 错误码到 HTTP 状态码的映射 |
| 字段边界 | 每个字段的长度、格式、必填性、取值范围 |
| 响应结构 | 统一响应信封（数据 / 错误 / 元信息） |
| 数据模型 | 实体、字段、关系、索引 |
| 设计条目 | 设计编号 → 模块 → 需求引用 → 契约引用 → 测试引用 |
| 非功能约束 | 性能、安全、并发要求 |

#### 2.2.5 讨论长度控制过程

| 约束 | 做法 |
|---|---|
| 单轮讨论有上限 | 硬性的最大轮次限制 |
| 每段有收敛条件 | 阶段间检查，不满足不前进 |
| 上下文不累积 | 用黑板保存观点 + 每轮摘要，不把完整历史塞进提示词 |
| 阶段间可暂停 | 避免一次性跑完整个讨论 |

### 2.3 阶段一到阶段二的衔接过程

衔接的唯一接口是**设计规格基线**。基线不是一份文件，而是一个带身份、带哈希、带父链的不可变对象。过程如下：

```text
阶段一运行结束（状态为完成）且 R1 已确认
    ↓
触发桥接：R1 → 设计规格
    ├─ 需求条目转换（保留编号、描述、验收条件、约束）
    ├─ 优先级归一化（各种写法统一为契约取值）
    ├─ 生成设计条目（设计编号 → 模块 → 需求引用 → 测试引用）
    ├─ 补全契约（接口 / 错误码 / 字段边界 / 响应结构 / 数据模型 / 非功能约束）
    └─ 组装基线对象（见下表）
    ↓
设计规格基线（可被阶段二直接消费）
```

**基线对象的字段**

| 字段 | 含义 | 为什么需要 |
|---|---|---|
| `baseline_id` | 基线唯一编号 | 下游按编号签收，不按文件路径 |
| `project_id` | 所属项目 | 同一项目多次运行共用一个 ID 空间 |
| `revision` | 该项目基线的递增序号 | 形成"同一需求的多版基线"链 |
| `parent_baseline_id` | 上一版基线 | 需求变更时可追溯"改了什么" |
| `r1_version` | 来源 R1 的版本 | 回到讨论阶段 |
| `design_spec` | 设计规格正文 | 阶段二的输入 |
| `sha256` | 规范化正文的内容哈希 | 任何一方的"版本一致"判断都用哈希，不用路径 |
| `confirmed_by` | 确认该版的 agent 角色 | 证明是 agent 共识而非人工勾选 |
| `generation_source` | `llm` / `rules` / `handwritten` | 区分来源，防止手写 fixture 冒充讨论产物 |

过程约束：

1. 只有"已完成且 R1 已确认"的运行才能进入第二阶段，否则拒绝。
2. 桥接产物必须携带**基线对象**，以便第二阶段的任务可以追溯回第一阶段的哪次讨论、哪一版需求；`generation_source=handwritten` 的基线只能作为阶段二的输入测试，不能充当端到端案例的证据。
3. 桥接只能做结构化转换，不得代替设计评审；未细化的契约字段必须在阶段一设计规格阶段补全，而不是留给第二阶段临时补齐。
4. 哈希必须对**规范化后的内容**计算（键排序、空白归一），否则"同一份内容"在不同侧会算出不同哈希。

### 2.4 阶段二过程：设计规格 → 编排 → 执行

#### 2.4.1 主流程

```text
设计规格基线
    ↓
[任务分解] 按需求条目与设计条目推导任务
    ├─ 设计条目 → 实现任务
    ├─ 契约操作 → 契约任务
    ├─ 需求条目 → 验收任务
    └─ 收尾 → 集成与交付任务
    ↓
[图编译] 为任务图补充结构节点
    ├─ 条件分支：按上游结果选择路径（pass / fail）
    ├─ 阶段检查点：阶段边界的可恢复锚点
    └─ 写入范围：每个实现任务声明允许写入的文件或目录
    ↓
[用户编辑] 增删任务、改依赖、改验收条件、改测试编号
    ↓
[计划校验] 编号唯一、依赖存在、无环、需求全覆盖、产物唯一所有者、
            写入范围不重叠或声明为串行、版本一致
    ↓
[计划登记] 生成计划版本，记录输入快照哈希；带"期望版本号"做并发控制
    ↓
[运行创建] 由计划创建任务运行；运行绑定它启动时的计划版本
    ↓
[调度推进] 依赖就绪 → 派发 → 执行 → 提交 → 验收 → 状态推进
    ├─ 通过 → 成功
    ├─ 失败 → 有限重试
    ├─ 条件不满足 → 跳过下游（skipped，不是失败）
    └─ 阻断 → 下游传播阻塞
    ↓
[可视化与回溯] DAG / 甘特 / 时间线 / 事件流、事件回放、断点恢复
    ↓
[发布] 网页端产物
```

#### 2.4.2 任务图的节点与边语义

任务图不只是"任务 + 依赖边"。为了表达条件执行和可恢复性，图中有四类节点、四种边：

| 节点类型 | 含义 | 状态机 |
|---|---|---|
| `task` | 由 agent 执行的工作单元 | 九态（见 2.4.3） |
| `decision` | 按上游结果选择分支的路由节点 | 随上游自动判定，不派发 |
| `checkpoint` | 阶段边界的物理锚点，记录提交号与快照 | 完成 / 未完成 |
| `join` | 多个并行分支的汇合屏障，全部到达才放行 | 完成 / 未完成 |

| 边类型 | 语义 |
|---|---|
| `dep` | 普通依赖：上游成功才允许下游 |
| `pass` | 条件满足时走的分支 |
| `fail` | 条件不满足时走的分支（可以通向修复或跳过） |
| `loop` | 有界返工：回到上游重做，受重试预算约束 |

过程要求：节点类型与边类型是**计划文档的字段**，由 B01 生成、B02 校验、B05 按类型渲染，而不是某一层代码里的特判。

#### 2.4.3 任务状态机
任务在运行中有九个状态，任何不在合法迁移表内的跳转都必须被拒绝：

| 状态 | 含义 |
|---|---|
| `PENDING` | 已登记，尚未评估依赖 |
| `READY` | 依赖全部成功，等待派发 |
| `RUNNING` | 已派发，执行中 |
| `WAITING_DEPENDENCY` | 依赖尚未完成 |
| `REVIEWING` | 已提交候选结果，等待验收 |
| `FAILED` | 执行失败且重试预算耗尽 |
| `RETRYING` | 失败但仍在重试预算内，等待重新派发 |
| `BLOCKED` | 上游失败/被阻断或存在阻断缺陷，暂停放行 |
| `SUCCEEDED` | 验收通过（终态） |

过程规则：

- 只有依赖全部成功才进入 `READY`；上游失败或被阻断，下游直接阻塞并记录阻塞原因。
- 处于执行中或待验收的任务**拒绝重复派发**。
- 每次派发都有尝试编号，尝试编号单调递增；重试计数只在失败重派时递增，且不超过任务的重试预算。
- **每一个状态变化都必须产生事件**，包括等待依赖与重试回队，否则事件回放会与快照不一致。
- 只读查询不写状态：查看"哪些任务可派发"是纯计算，要推进依赖必须显式调用推进动作。

#### 2.4.4 事件过程

事件是过程的唯一事实记录，事件类型固定枚举：

```text
就绪 / 派发 / 开始 / 提交 / 送审 / 通过 / 拒绝 / 安排重试
/ 阻塞 / 完成 / 失败 / 等待依赖
```

事件必须绑定任务、尝试编号、计划版本与输入快照；涉及提交与通过的还必须带提交引用。质量门产生的缺陷事件（缺陷创建 / 缺陷关闭）单独记录，不重复写入状态事件。

过程要求：同一语义只产生一条事件，且要保留"谁判定的"这一信息（判定结论以载荷形式挂在状态事件上，或体现为独立的缺陷事件）。

#### 2.4.5 执行与验收过程

```text
编排器构造执行请求（任务、尝试、计划版本、输入快照、目标、输入、输出、
                  验收条件、规定测试编号、写范围、超时、重试预算）
   ↓
执行侧返回执行结果（状态、产物、提交引用、证据引用、已知问题、
                    日志哈希、测试结果、耗时）
   ↓
质量门做九项必查
   1 任务字段完整性        2 需求覆盖        3 依赖环
   4 重复产物              5 版本一致性      6 日志哈希
   7 产物哈希              8 规定测试全部通过  9 提交引用合法
   ↓
判定：通过 / 驳回 / 需要重验
   ├─ 任一阻断问题 或 存在未关闭的阻断缺陷 → 驳回
   ├─ 版本或输入快照不一致（无阻断问题） → 需要重验
   └─ 只有一般/轻微问题 → 通过（问题保留在记录中）
   ↓
编排器消费判定并推进状态（唯一状态写入者）
```

过程约束：

- 执行侧的"成功"只代表"执行完成并自检通过"，**不等于验收通过**。
- 执行侧不得写状态、不得写黑板状态表，只返回结构化结果。
- 验收侧只返回判定与事件，不得直接改状态。
- 每条阻断问题只登记一次缺陷，去重键为"问题码 + 引用位置"；同一问题再次未复现时必须关闭缺陷，否则任务会被旧缺陷永久卡住。
- 哈希格式必须跨侧一致，避免"执行通过、验收必然拒绝"的错位。

#### 2.4.6 用户编辑编排内容的过程

| 步骤 | 要求 |
|---|---|
| 编辑 | 拖动节点位置、增删任务、连线/断线改依赖、修改验收条件与测试编号 |
| 校验 | 编辑后重新校验：依赖存在、无环、需求全覆盖、产物唯一所有者、写入范围不冲突 |
| 写回 | 通过接口写回后端，不原地修改已派发的计划 |
| 版本 | 每次编辑生成新的计划版本，保留版本链与输入快照 |
| 并发 | 写回时携带"期望版本号"（上次看到的版本）。服务端版本已前进则拒绝并返回当前版本，不静默覆盖 |

**并发控制过程**

```text
用户甲、乙同时基于计划 v3 编辑
    ↓
甲先提交：expected_revision = 3，服务端当前 = 3 → 通过，生成 v4
    ↓
乙后提交：expected_revision = 3，服务端当前 = 4 → 409 冲突
    ↓
乙的界面提示"计划已更新到 v4"，展示差异，由乙选择在 v4 上重做或放弃
```

过程要点：

1. 布局与数据分离，用户拖动位置不能被每次数据刷新覆盖。
2. 冲突必须是**可复现、可解释**的：错误里带当前版本号与冲突的字段，而不是一句"保存失败"。
3. 每个计划版本记录它所基于的**基线哈希**，运行创建时校验哈希一致，否则拒绝——这就是"上游输入变化不能用旧证据"在计划层的落地。

#### 2.4.7 产出软件的过程

| 环节 | 过程规定 |
|---|---|
| 产物形态 | 网页端应用（静态页面为起点，零构建依赖） |
| 产物位置 | 按运行编号归档到工作目录下 |
| 预览方式 | 由既有服务端静态托管，复用同一端口，不新开端口 |
| 验证方式 | 浏览器打开、核心功能可用 |

**真实执行的最小工程闭环**

模拟执行（`simulated=True`）只能证明编排正确，不能证明"产出了软件"。真实执行至少要满足以下过程规定：

| 环节 | 过程规定 | 不满足时的行为 |
|---|---|---|
| 隔离 | 每次尝试在独立工作区 / 分支内执行，基于已批准的上游产物 | 不在主工作区直接写 |
| 提交 | 产物以提交号登记；服务端校验提交可读、基于正确基线、只改了写入范围内的路径 | 校验不过视为执行失败，不登记产物 |
| 不伪提交 | 模型没返回正文、输出被截断、语法无效、没有新提交 → **不登记产物** | 记录失败原因（目标文件、请求上限、用量），进入重试 |
| 模型分档 | 规划 / 复核 / 集成用高能力模型；逐文件生成用低成本模型；大文件单独提高输出额度 | 额度不足是有界失败，不是静默截断 |
| 失败可见 | 失败记录包含目标文件、尝试编号、错误类型、可重试性 | 不能只给一句"执行失败" |

#### 2.4.8 案例迭代过程

```text
通用框架（领域无关）
   ↓
跑最小案例 → 发现问题 → 修框架
   ↓
跑简单案例 → 发现问题 → 修框架
   ↓
用完整流程自己生成中等 / 复杂案例（此时案例才可信）
   ↓
固定输入、可自动重跑、可对比
```

原则：**真正的目标不是"跑通某个案例"，而是"用流程自己生成案例"**。手写规格只作为阶段二的输入测试。

### 2.5 阶段三过程：可观测性与执行交互

#### 2.5.1 三块内容

```text
阶段三
├── A. 收编阶段一、阶段二的可视化（统一框架，不重做）
├── B. 观测数据
│     ├── 定义：执行过程中哪些数据要记录（schema）
│     └── 展示：怎么呈现这些数据
└── C. 执行交互
      ├── 圆桌交互（多 agent 与用户同场）
      └── 非阻塞：用户不响应时流程继续
```

#### 2.5.2 观测数据过程

观测数据模型按五要素组织：

```text
观测记录
├── 主体：运行 / 阶段 / 任务 / agent / 模型调用
├── 类型：状态变化 / 输入 / 输出 / 错误 / 指标
├── 时间：开始时间 / 结束时间 / 时长
├── 上下文：计划版本 / 输入快照 / 尝试编号 / 基线哈希
└── 载荷：结构化内容 + 关联引用
```

**模型调用是一等主体**

任务和阶段是被观测的，产生它们的每一次模型调用同样要被观测。每次调用落一条工件记录：

| 字段 | 含义 |
|---|---|
| `call_id` / `run_id` / `attempt_id` / `node_id` | 这次调用服务于哪个运行、哪次尝试、哪个节点 |
| `role` / `provider` / `model` | 哪个角色、哪个供应商、哪个模型 |
| `input_hash` | 输入（提示词 + 上下文）的规范化哈希 |
| `output_revision` / `output_hash` | 输出版本与内容哈希 |
| `usage` | 输入 / 输出 token 数 |
| `latency_ms` | 耗时 |
| `status` | 成功 / 有界失败（预算耗尽、需要输入）/ 技术失败 |

过程要求：

1. 讨论阶段的事件与任务编排阶段的事件必须进入**同一套观测体系**，并形成跨阶段时间轴，而不是各做各的。
2. 任何产物都能通过 `output_hash` 反查到产生它的模型调用，再通过 `input_hash` 反查到它读的输入版本。
3. 模型调用记录**可全文检索**，否则"上次为什么这么决定"只能靠翻日志。

#### 2.5.3 圆桌交互过程

| 对比项 | 阶段一的讨论 | 阶段三的圆桌交互 |
|---|---|---|
| 驱动方式 | 流程驱动（按 A—H 走） | 用户驱动（随时插入） |
| 发言顺序 | 预设角色顺序 | 用户点名 |
| 目标 | 收敛 | 澄清 |
| 阻塞性 | 不阻塞 | 不阻塞 |

用户在圆桌中可以：点名某个 agent 发言、追问某个观点、质疑并要求举证、让两个 agent 辩论、补充需求或纠正方向。整个过程不设审批按钮，用户不点"同意"，agent 自主推进。

#### 2.5.4 事后回溯过程

| 层次 | 内容 |
|---|---|
| 技术级 | 事件重放比对、断点恢复 |
| 因果级 | 产物 → 模型调用 → 输入版本 的反向追溯 |
| 业务级 | 耗时排名、重试热点、缺陷来源、不同运行的横向对比 |

### 2.6 贯穿全过程的三条控制规则

**规则一：唯一状态写入者**

```text
执行侧 → 只返回执行结果
验收侧 → 只返回判定与事件
编排器 → 唯一修改任务状态的角色
存储层 → 只做原子落盘与查询，不判断业务迁移是否合法
界面层 → 只发起控制指令并消费快照/事件，不直接改状态
```

这条规则保证事件流中"谁改的状态"永远唯一，避免同一语义出现两条事件。

**规则二：版本与证据链**

1. 需求、设计、契约、任务、计划都必须保留版本号**和内容哈希**；"版本一致"用哈希判断，不用路径或文件名。
2. 每次状态变化都有事件，事件可回放并与快照比对。
3. 断点恢复后不得重复执行已完成的任务。
4. 上游输入变化必须重新标记输入版本并重验，不能用旧证据充当新结论。
5. 模型回复、文件存在、多数意见都不能当作测试证据。
6. 可变记录（计划、运行）的写操作带期望版本号；内容版本与并发修订号是两个概念，分别使用。

**规则三：模拟与真实严格分离**

1. 模拟数据必须显式标注"模拟"，且不得被当作真实数据展示。
2. 真实接口失败时显示错误并清空，不静默回退成模拟数据。
3. 正式运行只使用单一端口，页面与接口同源。
4. 演示基线不得导入真实链路；真实执行需要模型而未配置时，以明确错误结束。

### 2.7 过程节点与产出对照

| # | 过程节点 | 执行主体 | 输入 | 动作 | 产出 | 校验 / 证据 |
|---|---|---|---|---|---|---|
| 1 | 需求输入 | 用户 + 框定 agent | 一句话想法 | 澄清、列假设、提开放问题 | 问题定义 | 假设清单完整 |
| 2 | 独立发散 | 多角色 agent | 问题定义 | 互不可见地出观点 | 观点列表 | 角色数量与独立性 |
| 3 | 聚类整合 | 主持人 agent | 观点列表 | 归并去重 | 候选方向 | 观点来源可追溯 |
| 4 | 结构化批判 | 多角色 agent + 质疑者 | 候选方向 | 赞同/反对/有条件赞同 | 异议列表 | 异议分类与归属 |
| 5 | 共识评价 | 评价 agent | 异议列表 | 打分；分歧则自动辩论 | 评价结果 | 评分维度与权重 |
| 6 | 方案审阅 | 起草 agent + 各角色 | 评价结果 | 起草并互相签核 | 方案草案 | 签核记录 |
| 7 | 需求确认 | 各角色 agent | 方案草案 | 各自表态，达成共识 | 需求规格 R1 | 表态记录与确认者 |
| 8 | 设计规格 | 设计 agent | R1 | 细化接口/错误码/字段边界/数据模型 | 设计规格 | 契约字段非空、可被阶段二消费 |
| 9 | 阶段桥接 | 编排器 | 已确认 R1 | 结构化转换 + 组装基线对象 | 可消费的设计规格基线 | 基线编号、内容哈希、父版本、确认者 |
| 10 | 任务分解 | 规划 agent | 设计规格基线 | 按需求/设计/契约推导任务与依赖，编译条件分支与检查点 | 任务计划 + 追溯表 | 需求全覆盖、无环、产物唯一、节点类型合法 |
| 11 | 编排编辑 | 用户 | 任务计划 | 增删任务、改依赖与验收 | 新版本计划 | 编辑后重新校验通过；版本冲突返回 409 而非覆盖 |
| 12 | 运行创建 | 编排器 | 计划 | 登记运行、冻结输入快照与基线哈希 | 任务运行 | 版本与哈希一致 |
| 13 | 依赖调度 | 编排器 | 运行 | 依赖检查、放行就绪任务 | 派发请求 | 不重复派发、尝试编号递增 |
| 14 | 受控执行 | 执行侧 | 执行请求 | 执行任务、产出工件 | 执行结果 | 返回结构合规、产物哈希 |
| 15 | 独立验收 | 质量门 | 执行结果 | 九项必查 | 通过 / 驳回 / 需重验 + 缺陷 | 证据与版本校验 |
| 16 | 状态推进 | 编排器 | 判定结果 | 通过、重试或阻断传播 | 状态与事件 | 每步有事件、可回放 |
| 17 | 可视化与回溯 | 展示层 | 运行快照与事件 | DAG / 甘特 / 时间线 / 事件流 | 过程视图 | 回放一致、断点可恢复 |
| 18 | 成果发布 | 交付层 | 运行结果 | 归档产物、静态托管 | 网页端产物 | 浏览器可打开、功能可用 |
| 19 | 观测与交互 | 观测层 | 全过程数据（含每次模型调用） | 统一观测、圆桌交互、事后回溯 | 观测视图 + 复盘 | 数据 schema 一致、产物可反查到调用、不阻塞 |
