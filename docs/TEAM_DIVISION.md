## 一、老师的原话

### 关于 222 分工

用户问：

> 另外我对老师您推荐的 222 分工不太明确，2 人完成阶段 1，2 人完成阶段 2，那么**剩下的 2 人分配什么工作**（因为我认为阶段 3 中 1、2 的可视化部分能够分配到阶段 1、2 中，所以剩下的 2 人不是单纯按照阶段 3 中任务进行分配，所以对此有些疑惑）

> 我还是建议，另外 2 人可以**做作业 3 的内容**，除了 1、2 的可视化部分，主要是**设计和实现执行过程中哪些数据需要记录、怎么展示**，也包括**执行交互部分**，比如**圆桌交互**，这些都属于作业 3 需要考虑的内容

用户担心：

> 因为我想让这 3 组能够同时执行任务，而作业 3 总的来说是对 12 各个方面的优化，这样的话完成作业 3 的那 2 人也许要等候作业 1、2 的完成，这样的分工不太能三组并发执行

### 关于分组的灵活性

老师用一个比喻说明：

> 我提的分工想法是因为**可视化部分又不影响 12 流程的优化，可以独立为 3**，比如，**你装修一个会议室又不影响你会议流程，等装修好了再搬到新会议室就行**。分工你们自己决定，我的**仅供参考**。

## 二、可以采用的两种分工

老师给了两个方案，都可行。

### 方案 A：222 分工（老师建议）

```text
组 1（2 人）  阶段 1：需求 → 讨论 → 设计规格
                + 阶段 1 的可视化
组 2（2 人）  阶段 2：设计规格 → 编排 → 执行
                + 阶段 2 的可视化
组 3（2 人）  阶段 3：观测数据设计 + 展示
                + 执行交互（圆桌交互）
                + 收编 1、2 的可视化
```

**老师对方案 A 的评价**：组 2 内容明显会多。

**优点**：
- 每个阶段的责任人清晰
- 阶段 1、2 的可视化与流程一起做，不会脱节
- 组 3 专注"观测 + 交互"这个独立命题

**缺点**：
- 组 2 工作量最大（编排 + 执行 + 可视化）
- 组 3 需要等 1、2 的可视化完成才能收编（虽然老师认为装修不影响会议）

### 方案 B：33 分工（可视化归 1/2）

```text
组 1（2 人）  阶段 1 流程 + 阶段 1 可视化
组 2（2 人）  阶段 2 流程 + 阶段 2 可视化
组 3（2 人）  阶段 3：观测数据 + 执行交互 + 统一框架（不含各阶段可视化）
```

**本质与方案 A 相同**，只是明确了"可视化由各阶段自己做"。

老师对用户这个理解的回应是：

> 你这样理解你分 33 也行啊，可视化部分分割到 1/2 去

### 我的建议

**采用方案 A，但把组 2 的一部分工作提前分给组 3**：

| 从组 2 移出的工作 | 移到 | 理由 |
|---|---|---|
| 观测数据收集（执行阶段的数据埋点） | 组 3 | 这正是组 3 的核心命题，且不依赖编排逻辑完成 |
| 执行交互的界面 | 组 3 | 同上 |

这样组 2 只负责：分解 + 编辑 + 编排 + 推执行，工作量更平衡。

## 三、三组的具体职责

### 3.1 组 1（2 人）：阶段 1

**目标**：用户输入需求 → 多方 agent 讨论 + 用户实时交互 → 输出**尽可能细化**的设计规格

**关键约束（老师第二轮确认）**：
- **全自动化，无人工介入** → 现有 3 处 `WAITING_HUMAN` 审批门必须改造
- **用户交互是非阻塞的** → 用户不响应时流程继续
- 设计规格**尽可能细化**（接口、错误码、字段边界、数据模型）

| # | 工作项 | 优先级 | 估时 |
|---|---|---|---|
| **1-1** | **拆除 3 处人工审批门 + 六人确认改 agent 确认** | **P0** | 18h |
| **1-2** | **并行式用户-agent 对话通道 + SQL 记忆** | **P0** | 22h |
| **1-3** | **H 阶段：细化的设计规格产出** | **P0** | 20h |
| 1-4 | 简化模式（跳阶段，向下兼容） | P0 | 8h |
| 1-5 | 思考过程可视化（含用户修改入口） | P0 | 18h |
| 1-6 | 讨论离线 fixture | P1 | 4h |

**合计：约 90h**

**估时说明**

| 项 | 变化 | 原因 |
|---|---|---|
| 1-1 | 16h → 18h | 「六人确认」不再是简单拆门，而是要重设计成 agent 互相确认（含语义保留） |
| 1-2 | 20h → 22h | 新增 SQL 对话记忆表 + 消费机制 |
| 1-5 | 16h → 18h | 用户可修改 agent 产出（Q1b），需要编辑入口 |

**两人分工**：

| 人 | 负责 | 理由 |
|---|---|---|
| 甲 | 1-1 拆审批门、1-2 对话通道与记忆、1-4 简化模式 | 都在讨论状态机与存储层，需要一个人贯通 |
| 乙 | 1-3 设计规格、1-5 可视化与编辑、1-6 fixture | 产出物与呈现，相对独立 |

**1-1 的具体改造**（`b02-workflow-agent/backend/controller.py`）：

| 行号 | 现有 | 改为 |
|---|---|---|
| `:170` | EVALUATE 分歧 → `WAITING_HUMAN` | agent 自动辩论 N 轮 → 自动判定 |
| `:195` | PROPOSAL_REVIEW 被拒 → `WAITING_HUMAN` | 自动修订重试（有限轮次） |
| `:208` | HUMAN_CONFIRMATION → 等六人勾选 | **agent 角色互相确认** |

**六人确认的改造细节**（用户已明确「唯一的人只有用户」）：

| 层 | 现状 | 改为 |
|---|---|---|
| `MEMBERS` | `("成员 A", ..., "成员 F")` 人类名 | agent 角色 ID（`PM-01`, `ARCH-01`, `USER-01`, `DEVIL-01` 等） |
| `publish()` | 要求六人全勾选 | 要求所有 agent 角色 agree（或含条件同意） |
| 前端 | 六个 check box | agent 表态卡片（显示 stance + 理由） |
| 用户 | 无入口 | 对话输入框（可质疑，触发重新表态） |

**关键**：保留「多角色参与」的形式与「异议必须解决」的门槛，只把**判定者从人换成 agent**。

**两人分工**：

| 乙 | 2-2 真实执行与网页产出、2-4 并行批次、2-5 通用性测试 | 都在执行链路上 |

**关于「产出网页」的技术方案**（已收敛）

用户明确「技术栈按你推荐的来；不用真的制作软件，制作一个网页端即可；暂时不用（部署）」。

**推荐方案**：

```text
产物：单个 index.html（内联 CSS + 原生 JS，零构建依赖）
位置：work/deliverables/<run_id>/index.html
预览：B02 静态服务加路由 GET /preview/<run_id>/ （复用 7100 端口）
验证：浏览器打开，手工点几下确认功能可用
```

**为什么这样选**：

| 考虑 | 说明 |
|---|---|
| 最少依赖 | 不需要 npm、不需要构建步骤 |
| 最易验证 | 一个文件，双击就能看 |
| 符合单端口约束 | 由 B02 托管，不开新端口 |
| 够用 | 课程要求是"网页端即可"，不是生产级应用 |

**2-6 案例重建的说明**（用户重要提示）

用户指出：

> 当前生成出的案例并没有经过与用户的交互，也没有经过多智能体讨论，这些案例是不完整的，校园失物目前大概只能到 L2。

代码核实确认：`campus-lost-found.spec.json` 等**都没有 `phase1_source` 字段**，是手写 fixture。

所以需要一个专门的环节：**用完整流程重跑，生成真正经过讨论的案例**（C2/C3 级），而不是继续用手写样例充当案例。

## 五、但老师还有一个更重要的建议

### 5.1 「先跑通再迭代」

老师在对话结尾：

> **不用太急，多想想，先跑通再迭代优化**

以及：

> 我们后续肯定都是通过**跑项目案例，迭代优化流程**，不然**空对空没有任何实际意义**

### 5.2 这对分工的影响

**如果三组立刻分头开工，会重蹈"空对空"**：

- 组 1 做完讨论，阶段 2 消费不了设计规格
- 组 2 做完编排，执行还是 mock
- 组 3 做完观测框架，前两步没有数据可观测

### 5.3 排期方式：同样是这些任务，分两段推进

**重要澄清**：下面不是「分工之外的新工作」，而是**把第三节的任务表按时间排序**。每一项都能在 3.1—3.4 的工作项里找到编号。

#### 第一段（1—2 周）：先让链路通

| 时间 | 做什么 | 对应工作项 | 谁 |
|---|---|---|---|
| 第 1 周前半 | 前端拆分、可视化规范、契约冻结 | 0-1、0-2、0-3 | 组 3 乙、组 2 甲 |
| 第 1 周后半 | L1 案例定义 | 0-4 | 组 2 甲主导 |
| 第 1—2 周 | 拆审批门 + 六人确认改 agent 确认 | **1-1** | 组 1 甲 |
| 第 1—2 周 | 并行式对话通道 | **1-2** | 组 1 甲 |
| 第 1—2 周 | 设计规格产出（先做"够用"版） | **1-3** | 组 1 乙 |
| 第 1—2 周 | 真实执行 + 产出网页 | **2-2** | 组 2 乙 |
| 第 1—2 周 | 观测埋点（先记录，后展示） | **3-2** 的前半 | 组 3 甲 |

**第一段结束的标志**：能用 L1 案例从需求跑到网页产物。

注意此时 **1-3 只做"够用"版**（不追求接口/错误码全细），**3-2 只埋点不展示**，**2-1 编辑还没做**。这些留到第二段。

#### 第二段（3—6 周）：在通了的链路上深化

| 组 | 深化哪些工作项 |
|---|---|
| 组 1 | 1-3 细化（补接口/错误码/字段/数据模型）、1-4 简化模式、1-5 可视化、1-6 fixture |
| 组 2 | 2-1 编辑回写、2-3 增量分解、2-4 并行批次、2-5 通用性测试、2-6 案例重建 |
| 组 3 | 3-1 schema 定稿、3-2 展示部分、3-3 圆桌交互、3-4 统一框架、3-5 回溯 |

**两段的工作量关系**：

| 组 | 第一段 | 第二段 | 合计 |
|---|---|---|---|
| 组 1 | 约 40h（1-1 18 + 1-2 22） | 约 50h | 90h |
| 组 2 | 约 20h（2-2 主体） | 约 58h | 78h |
| 组 3 | 约 20h（3-2 埋点） | 约 66h | 86h |
| 共同准备 | 18h（0-1～0-4） | — | 18h |
| **合计** | **约 98h** | **约 156h** | **254h** |

**为什么这样排**：老师说的「空对空」风险是真实的——如果组 1 把设计规格做到最细，组 2 却还没接真实执行，就不知道"细到什么程度够用"。先粗后细，边跑边定。
