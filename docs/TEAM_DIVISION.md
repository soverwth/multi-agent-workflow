# 团队分工方案

> 基于：三次课堂作业要求（`HOMEWORK_SCOPE.md`）、当前项目实际能力、待澄清问题（`OPEN_QUESTIONS.md`）。
> 分工形式：**每个作业 2 人，共 3 组 6 人**（老师要求）。
>
> **本文的结论是"建议方案"，不是最终决定。** 标注了哪些部分取决于尚未确认的问题。

---

## 一、分工的基本原则

### 1.1 按作业分，不按代码目录分

现有代码的模块**同时服务多个作业**：

```
B01 规格规划  → 作业1（需求规格）+ 作业2（任务分解）
B02 编排      → 作业1（讨论状态机）+ 作业2（任务编排器）
B03 状态/事件 → 作业2 + 作业3
B04 执行      → 作业2
B05 可视化    → 作业3（但含作业1、2的页面）
B06 质量门    → 作业1（共识评价）+ 作业2（任务验收）
```

如果按目录分工，会出现「同一个人同时服务三个作业」，与「每作业 2 人」矛盾。

**所以按作业的交付物分工**，代码可以共享。

### 1.2 三个组共享同一条主线的风险

最大的协作风险是：三组同时改 `frontend/src/App.tsx`（约 1000 行）。

**必须先做前端结构拆分**（见第七节），否则建议先不要并行开工。

## 二、总体结构

```text
┌─────────────────────────────────────────────────────────────┐
│  组 1（2 人）  作业 1：用户需求 ─(多智能体讨论 + 多轮对话)→ 设计规格 │
│  组 2（2 人）  作业 2：设计规格 → 任务分解 → 编排 → 执行可视化与控制 │
│  组 3（2 人）  作业 3：可观测性框架（收编 1+2 的可视化 + 拓展）      │
└─────────────────────────────────────────────────────────────┘
              ↓ 组 1 产出设计规格（作业 2 的输入）
              ↓ 组 3 收编 1、2 的可视化
```

**串联关系**：
- 组 1 → 组 2：通过 `phase_bridge`（需补全 `contract`，见 Q4）
- 组 1 + 组 2 → 组 3：通过统一的观测接口
- 组 3 需要**先出可视化规范**，否则 1、2 各做各的，收编时返工

**三组的核心难点各不相同**：
- 组 1 难在**交互形态**（怎么和用户多轮对话而不打断讨论）
- 组 2 难在**执行的真实性与可控性**
- 组 3 难在**统一三套异构可视化的表达**

## 三、组 1：作业 1（2 人）

### 3.1 目标

**用户输入一个需求 → 通过多智能体讨论与多轮用户交互 → 输出需求规格（设计规格）。**

这是作业 1 的完整定义。注意三个关键词：
- **多轮用户交互** —— 不是跑一遍固定流程
- **多智能体讨论** —— 完成这个任务推荐的方式（Autogen2 是可选项）
- **输出设计规格** —— 作业 2 的直接输入

### 3.2 现状

| 项 | 状态 |
|---|---|
| 讨论状态机（A—H 八阶段） | ✅ 完成 |
| 四角色独立发散 + 聚类 + 结构化批判 | ✅ 完成 |
| 六人确认 → R1 发布 | ✅ 完成 |
| 真实模型接入（DeepSeek） | ✅ 完成，已实测 |
| **与用户的多轮交互** | ❌ **只有 2 个固定介入点，无中途对话** |
| **输出可用的设计规格** | ⚠️ 有 R1 需求列表，但 `contract` 为空 |
| 讨论过程的可视化 | ⚠️ 只有真实接口模式，无离线数据 |
| Autogen2 | ❌ 未使用（推荐方式，非必须） |

### 3.3 待完成的工作

**按重要性排序**。1-1 是核心缺口。

| # | 工作项 | 说明 | 估时 | 依赖 |
|---|---|---|---|---|
| **1-1** | **对话式需求澄清** | 讨论中途可暂停等用户回答；用户补充约束后继续讨论 | 20h | Q0 |
| **1-2** | **设计规格补全** | 用 SE-lib 的 Schema 作蓝本，补 `contract.operations` / `errors` / `field_bounds` | 14h | Q4 |
| 1-3 | 讨论过程可视化 | 阶段进度、观点流、异议状态、共识度曲线 | 16h | 前端拆分 |
| 1-4 | 讨论离线 fixture | 生成真实讨论快照，支持无 Key 演示 | 4h | 1-3 |
| 1-5 | Autogen2 适配 | **可选**，仅在确认有评分收益时 | 20h+ | Q1 |

**合计**：约 **54h**（不含 Autogen2）。

### 3.4 两个人怎么分

**推荐方案：按「对话机制 / 规格产出 + 可视化」切**

| 人 | 负责 | 理由 |
|---|---|---|
| **甲（交互与状态机）** | 1-1 对话式需求澄清 | 涉及讨论状态机改造（加"等待用户"状态）、B02 接口、前端对话 UI。这是作业 1 最核心也最难的部分，需要一个人专注 |
| **乙（规格与可视化）** | 1-2 设计规格补全、1-3 可视化、1-4 fixture | 1-2 是组 1→组 2 的接口，1-3 是组 3 要收编的内容 |

**为什么这样分**：
- 1-1 是**纵向贯穿**的（状态机 → API → 前端），拆开会导致反复沟通成本
- 1-2 / 1-3 相对独立，可以并行

**若 Q0 确认"交互很简单"**（如只要 2—3 个固定检查点），可下调 1-1 到 8h，届时两人可均分。

### 3.5 交付验收

- [ ] 输入一句模糊需求，系统能**追问**，用户回答后继续
- [ ] 讨论过程中用户能**随时**补充约束或纠正方向
- [ ] 六人确认后发布需求规格
- [ ] **输出的设计规格能被组 2 直接消费**（含接口定义、错误码、字段边界）
- [ ] 无 API Key 时也能演示（用 fixture）
- [ ] 讨论过程可视化完整（观点、异议、批判、共识度）

## 六、三组的协作接口

### 6.1 组 1 → 组 2

**接口**：`phase_bridge` 产出的 design spec

**关键约定**：
- 当前 `contract.operations` / `errors` / `field_bounds` 为空
- 需补全到什么**粒度**，取决于 Q4 的答案
- 补全时**参考 SE-lib 的 `design-spec.schema.json`** 的字段组织方式（见 `REFERENCE_PROJECTS.md` 3.2）
- **组 2 可以先用现成设计规格开发**（老师建议的解耦方式），但**最终必须能消费组 1 的产出**

**建议的对接节奏**：
1. 第一周：组 1 乙 与组 2 甲 共同确认 design spec 的字段清单
2. 第二周：组 1 产出第一版完整规格，组 2 用它跑通分解
3. 后续：规格变更需双方确认

### 6.2 组 1 + 组 2 → 组 3

**接口**：事件流 + 任务状态 + 阶段进度 + **用户交互记录**

**关键约定**：
- 组 3 需要定义"什么是可观测的原子事件"
- 现有的 `TASK_*` 事件类型（12 种）需要扩展以覆盖讨论阶段吗？
- **新增**：组 1 的对话交互（用户提问、系统追问、用户回答）也要能被观测，是否作为一种新事件类型？
- 组 3 的 3-1 规范要在**第 1 周内**定稿并同步

### 6.3 冲突高发区

| 区域 | 风险 | 缓解 |
|---|---|---|
| `frontend/src/App.tsx` | 三组都改 | **前端结构拆分**（第七节） |
| `b02-workflow-agent/backend/controller.py` | 组 1 加对话状态、组 3 加观测 | 组 1 主导，组 3 只读 |
| `b02-workflow-agent/backend/task_orchestrator.py` | 组 2 改控制、组 3 改观测 | 组 2 主导，组 3 只读 |
| `docs/TASK_ORCHESTRATION.md` | 契约变更 | 变更需三组会签 |

## 七、开工前必须先做的事

### 7.1 前端结构拆分（阻塞项）

**现状**：`frontend/src/App.tsx` 约 1000 行，包含 8 个页面的全部逻辑。

**问题**：三组同时改必然天天冲突。

**方案**：把 8 个页面各自拆成独立组件文件，`App.tsx` 只保留状态与路由。

```
frontend/src/
├── App.tsx                    # 只做状态管理 + 页面路由（预计 < 300 行）
├── pages/
│   ├── ProjectOverviewPage.tsx
│   ├── OwnerPage.tsx
│   ├── RequirementsPage.tsx
│   ├── SpecPage.tsx
│   ├── OrchestratePage.tsx
│   ├── AgentsPage.tsx
│   ├── DeliveryPage.tsx
│   └── HistoryPage.tsx
└── components/                # 复用组件
```

**估时**：4—6 小时
**建议**：由组 3 的甲负责（因为他要定可视化规范，最需要统一的组件边界）

### 7.2 可视化规范（阻塞项）

组 3 的 3-1 必须先出，否则组 1、2 的界面做完了还要改。

**产出**：
- 状态色板（九态 + 讨论八阶段）
- 事件表达的视觉规则
- 时间轴 / 进度条的组件接口
- 页面布局的栅格规范

**估时**：6 小时
**建议**：第一周内定稿，三组评审

### 7.3 接口契约冻结（阻塞项）

`docs/TASK_ORCHESTRATION.md` 是唯一跨块契约。组 2 和组 3 都要碰状态与事件，必须先确认：

- 事件类型要不要扩展（覆盖讨论阶段）？
- 运行快照要不要加观测字段？

**建议**：组 2 甲 + 组 3 甲共同起草，第一周内冻结。

## 十、这个方案的不确定性

标注哪些结论依赖未确认的问题：

| 结论 | 依赖 | 不确定度 |
|---|---|---|
| 组 1 工作量 54h | **Q0（交互复杂度）**、Q1（Autogen2） | **高**：交互若很复杂可能 +20h |
| 组 1 的形态是否正确 | **Q0** | **极高**：若老师要的是"固定检查点"而我们做了"自由对话"，或反之，都要返工 |
| 组 2 工作量 66h | Q2（控制程度）、Q3（真实执行） | **高**：可能减三分之一 |
| 组 3 工作量 56h | Q7（回溯深度） | 中：可能减 12h |
| 组 1→2 串联可行 | Q4（规格精度） | 中：已确认要产出，只需确认粒度 |
| 三组可并行 | 前端拆分是否做 | **高**：不做则冲突严重 |

### 最该先问的

**Q0（与用户多次交互的具体形态）** 是唯一可能导致「方向性返工」的问题。其余问题的答案只影响工作量，Q0 影响的是**做成什么样**。

**建议**：在写任何代码之前，先拿 Q0 去问老师。
