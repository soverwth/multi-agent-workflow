## 一、三次作业的原始要求

要求来自任务文档中的课堂幻灯片照片与文字说明。

### 作业 1

**流程**
```
想法 - 多体讨论 - 建设方案 - 多方评价 - 需求规格（需求确认）
```

**核心目标（用户确认）**

> 用户输入一个需求，最后输出一个**需求规格（设计规格）**。
> 通过**多智能体讨论**（可采用 Autogen2）是完成这个任务推荐的一个方式。
> 中途需要**与用户进行多次交互**。

要点：
- **输入**：用户的一个需求（想法）
- **输出**：需求规格 / 设计规格（这是作业 2 的输入）
- **手段**：多智能体讨论 —— 推荐方式，非唯一
- **过程**：需要与用户多轮交互（不是一次性的）

**参考实现**：老师推荐其他组的 `https://github.com/cocoliler/SE-lib`，说的是**参照它的工程规范**（契约管理、文档组织、验收证据），功能实现用我们自己的。详见 `REFERENCE_PROJECTS.md`。

### 作业 2

**流程**
```
设计规格 - 开发任务分解 - 开发任务编排（编排器）- 执行可视化和控制
```

**明确要求**
- （流程设计）设计规格 → 任务分解 → 编排器 → 执行可视化 / 执行交互
- （设计验证）完成上述设计的原型
- 团队项目 Git

### 作业 3（w11）

**原文**
> 多智能体软件工程工作流（Multi-Agent SE workflow）的可观测性（可视化）框架，具体包括：课堂作业 1 和 2 的可视化部分，以及执行阶段的观测数据、执行交互等，进一步也可以考虑事后回溯等。

**用户补充确认**：任务 3 = 对 1、2 进行可视化 + 拓展。

**同期幻灯片还有一行**：`〈智能体评测〉主讲：计浩晟` —— 这是讲课主题，不是作业要求，但可能影响评分侧重。

### 扩展考虑（非必做）

幻灯片列出的三条扩展方向：
1. 需求变更流程设计
2. 开发任务编排器详细设计
3. 环境监听（如关于新讨论 / 用户反馈）、提炼与评价

用户确认：**不是必做，优先级靠后，后续优化时大概需要**。

### 作业 1 的三个要点

按用户澄清，作业 1 有三处必须理解正确的地方。

#### 要点 1：核心是「对话式需求澄清」

作业 1 不只是「跑一遍讨论」，而是**用户参与的多轮交互**：

```text
用户需求
   ↓
多智能体讨论（四角色独立发散 → 聚类 → 批判 → 评价）
   ↓  ←──── 与用户交互（澄清、裁决、补充约束）
建设方案 Proposal
   ↓
多方评价
   ↓  ←──── 与用户交互（确认、修订）
需求规格 / 设计规格（作业 2 的输入）
```

**与当前实现的差距**：现状有 3 处人工审批门（价值分歧的「人类裁决」、Proposal 审阅被拒、需求确认的「六人确认」），这些都被老师后续澄清否决——**项目是全自动化的，没有人工介入**，只有用户与 agent 的对话交互。所以这些门要改造为 agent 自动判定 + 用户可随时插话。

**详细需求见** [`PROJECT_REQUIREMENTS.md`](PROJECT_REQUIREMENTS.md)。

#### 要点 2：终点是「设计规格」，不只是「需求列表」

用户明确：作业 1 **最后输出一个需求规格（设计规格）**，作业 2 拿它当输入。

这意味着：
- 当前 R1 只有 `req_id` / `description` / `priority` / `acceptance`
- **不足以支撑作业 2 的任务分解**（缺接口定义、错误码、字段边界）
- `phase_bridge` 的 `contract` 字段目前全空，需要补全（见 5.2）

#### 要点 3：Autogen2 是推荐方式，不是唯一方式

作业 1 幻灯片列了 `Autogen2`，用户澄清为「可采用 Autogen2」的**推荐方式**。

当前项目用自研状态机 + 共享黑板实现，**功能上满足要求**。是否改用 Autogen2 取决于：
- 老师对「推荐」的权重如何认定
- 自研方案是否能在文档中充分论证（可靠性、可控性）

`OPEN_QUESTIONS.md` 的 Q1 仍值得确认，但不再是「必须返工」的阻断项。

## 五、必须了解的结构性问题

### 5.1 模拟数据下没有讨论过程可视化

`RequirementsView.tsx` 的实现里有明确判断：

```tsx
演示数据快照只含任务编排结果，不含讨论过程。
请切换到「真实接口」查看真实需求与方案。
```

**含义**：`taskRunFixture.json` 是**第二阶段编排产物**，不含第一阶段的讨论数据。所以：

- 打开页面默认看到的是编排 DAG，**看不到作业 1 的讨论过程**
- 要看作业 1 的内容，必须切到「真实接口」并真的跑一次讨论

**对作业 3 的影响**：如果作业 3 要「对 1 的可视化」，当前没有可用的离线演示数据。要么补讨论 fixture，要么作业 3 必须在线演示。

### 5.2 `phase_bridge` 产出的是「需求级」而非「设计级」规格

`b02-workflow-agent/backend/phase_bridge.py` 的转换结果：

```python
"contract": {
    "contract_version": ...,
    "operations": [],        # 空
    "errors": {},            # 空
    "field_bounds": {},      # 空
    "response_envelope": {}, # 空
}
"design_entries": [{
    "design_id": "DS-REQ-01",
    "module": "mvp/...",
    "contract_refs": [],     # 空
    "rule": "实现并验证 ...；具体技术方案由设计规格评审补充。",  # 占位文字
}]
```

作业 1 的终点确实是「**需求**规格（需求确认）」，所以这不算 bug。但作业 2 的输入叫「**设计**规格」，两者的差距（接口定义、错误码、字段边界）需要有人补。

**这是作业 1 → 作业 2 串联时绕不开的一段工作**，归属待定（见 `OPEN_QUESTIONS.md` Q6）。

### 5.3 界面 8 步与实际 8 阶段不是一一对应

02 页顶部的流程条：

```
1 用户想法  2 多体讨论  3 R1 确认  4 设计规格
5 任务分解  6 任务编排  7 执行验收  8 可视化
```

而 B02 讨论状态机实际是 A—H：

```
A INTAKE  B DIVERGE  C CLUSTER  D CRITIQUE
E EVALUATE  F PROPOSAL_REVIEW  G HUMAN_CONFIRMATION  H COMPLETED
```

映射关系不成立：

| 流程条 | 对应实际阶段 |
|---|---|
| 1 用户想法 | A INTAKE |
| 2 多体讨论 | B + C + D（三个阶段） |
| 3 R1 确认 | E + F + G（三个阶段） |
| 4—8 | **不属于 A—H**，跳到第二阶段和视图 |

**对作业 3 的影响**：可观测性框架需要知道「当前在第几步」。现在的进度条是**静态装饰**，不反映真实状态。这在做作业 3 时必须先修正。

### 5.4 B04 真实 runner 未接入

`STAGE2_STATUS.md` 自述：

> B04 真实 runner 尚未接生产模型。`gateway.py` 提供了 `runner_callable` 注入位与结果契约校验，但未构造真实的 `AgentRunner` envelope 与 manifest 转换。演示与测试一律使用显式标注 `simulated=True` 的确定性 mock 执行器。

**影响**：作业 2 要求的「执行可视化和控制」，可视化的是一段**模拟执行**。课堂演示可用，但如果老师要求看真实执行就撑不住。

## 七、作业与工作块的对应关系（供分工参考）

```text
作业1 ──────────────► B01（部分）+ B02 讨论状态机 + B06 共识评价
```
