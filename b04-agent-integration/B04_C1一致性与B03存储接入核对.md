## 3 确认的问题清单

### F01 · P2 · 已修复：服务端 HTTP 异常被改写为客户端字段错误

位置：[app.py](<./src/b04/reference_backend/app.py>) 的 `transport_error`；以下保留修复前的复现证据。

修复前的处理逻辑把 404 以外的所有 `werkzeug.exceptions.HTTPException` 都映射为 `400 / INVALID_FIELD`。因此，`InternalServerError` 等服务端 5xx 异常不会进入后面的通用异常处理器。

补充探测：在实际 `SQLiteUnitOfWork.add_lost` 完成插入后注入 `InternalServerError`，再调用合法发布接口。

| 项目 | 结果 |
| --- | --- |
| C1 预期 | `500 / INTERNAL_ERROR`，field=null，事务回滚 |
| 修复前实际 | `400 / INVALID_FIELD`，field=null |
| 数据变化 | 已回滚，未留下新增失物 |
| 影响 | 将服务端故障错误归因于请求字段；接入其他基于 HTTP 异常的适配层时尤其需要避免 |

修复后仅对已知请求／认证／路由异常作明确映射；服务端 5xx 和无法分类的异常统一为 `500 / INTERNAL_ERROR`、field=null，不输出底层详情。通用 HTTP 409 不能推断属于哪一种 C1 业务冲突，按未预期异常处理；已明确的 ApiError 仍分别返回三个 C1 的 409 业务错误。Flask 默认绕过处理器的无码 HTTPException 也会进入 C1 错误处理，避免返回 HTML／200。新增四类写操作的故障注入验证了事务回滚。

### F02 · P2 · 已修复：含 U+0000 的字符串通过业务校验后意外返回 500

位置：[contracts.py](<./src/b04/reference_backend/contracts.py>) 的文本校验与 [repository.py](<./src/b04/reference_backend/repository.py>) 的长度 CHECK；以下保留修复前的复现证据。

合法 JSON 字符串 `"\u0000A"` 解码后为两个字符。业务 `text()` 按 Python 字符长度校验会接受，而 SQLite 的 `length()` 在第一个 U+0000 处终止计数，结果为 0，从而触发 CHECK 失败。

已复现：

| 输入位置 | 实际结果 |
| --- | --- |
| register.nickname=`"\u0000A"` | `500 / INTERNAL_ERROR` |
| update_me.nickname=`"\u0000A"` | `500 / INTERNAL_ERROR` |
| publish_lost.name／description／location=`"\u0000A"` | 均为 `500 / INTERNAL_ERROR` |
| create_claim.statement=`"\u0000A"` | `500 / INTERNAL_ERROR` |

修复前上述输入均未留下部分业务写入，但错误行为未与 C1 对齐。C1 当前只规定类型、去空白和字符长度，并未明确禁止 U+0000；JSON 的 null 与字符串中的 U+0000 也不是同一概念。

本次严格遵循当前 C1，没有添加禁用字符规则，也没有删除或替换字符串中的 NUL。B04 的每个 SQLiteRepository 连接注册完整字符计数的 SQL length 函数，使现有 TEXT CHECK 与 Python 字符长度校验一致。该调整只在本地参考连接生效，兼容现有参考数据库，不重建表、不重写数据，也不修改 B03 存储。回归覆盖正常保存／读取／搜索、字符上限、数据库直接写入仍受 CHECK 约束，以及重启后的数据保留。实际 B03 数据库仍须单独验证这一字符语义；未来若要禁止字符，必须先更新团队契约。

## 4 B03 接入状态与职责区分

团队文档第 10.3 节要求 B03 提供两类存储：

| 层次 | B03 交付职责 | B04 消费方式 |
| --- | --- | --- |
| 通用平台 | task_store、artifact_store、事件、快照、租约和版本有效的产物读取 | agent_runner／tool_executor 的平台端口 |
| 测试产品 | 案例 T02 用户、失物、申请模型及数据约束 | 本参考后端的业务 Repository／UnitOfWork 适配器 |

这两类数据必须分开。现有 [SQLiteRunnerStore](<./src/b04/agent_runner/store.py>) 是 B04 的平台参考实现，不具备业务 Repository 的 `transaction(write=...)` 和用户／失物／申请／会话方法，不能作为 T03–T05 仓储直接传入。平台 artifact_ref 也不能直接替代业务 UUID。

当前 [Repository／UnitOfWork](<./src/b04/reference_backend/repository.py#L23>) 是 **B04 提出的本地消费端口**，不是已经由 B03 发布并确认的正式接入协议。`create_app(repository=...)` 提供了注入点，但有注入点不等于已经完成对接。

### 5.1 UnitOfWork 方法集合

当前共有 13 个方法：

- 用户：user、user_by_account、add_user、update_nickname。
- 会话：session、add_session、revoke_session。
- 失物：lost、add_lost、list_lost。
- 申请：claim、add_claim、list_claims。

`list_lost`／`list_claims` 返回 `(rows, total)`，由 B04 组装 C1 分页响应，不能直接返回 ORM 分页对象或已包装的 HTTP data。

### 5.2 行数据最小字段与类型边界

| 记录 | B04 当前需要的字段 |
| --- | --- |
| User | id、account、password_hash、nickname、created_at |
| LostItem | id、publisher_id、name、description、location、lost_at、status、created_at |
| ClaimApplication | id、lost_item_id、applicant_id、statement、status、created_at |
| Session | token_hash、user_id、created_at、expires_at、revoked_at（可为 null） |

私有字段仍由服务端用于认证、权限和关联检查，不能在数据库读取时提前裁剪成公开 UserView／LostView。公开响应再由 B04 投影过滤。

特别注意 [auth_profile.py:92](<./src/b04/reference_backend/auth_profile.py#L92>) 直接比较 `session['expires_at']` 与标准化 UTC 字符串。补充探测仅将 expires_at 改为原生 aware datetime，合法会话访问 `/me` 即变成 `500 / INTERNAL_ERROR`。这证明需要类型转换层；**并不证明尚未提供的 B03 实现存在该缺陷**。返回带偏移或不同精度的时间字符串也不能靠字典序可靠比较。

### 5.3 唯一约束与会话接入

服务层只捕获本目录定义的 DuplicateAccount／DuplicateClaim。B03 使用其他数据库驱动时，应按具体约束转换异常，而不是将所有 IntegrityError 都当作同一个重复错误。普通唯一异常若直接穿透，会变成 500。

如果 B03 的 T02 只提供 C1 的三种业务实体，而会话由 T03 单独保存，需要先明确组合仓储如何实现当前 UnitOfWork 的会话与用户访问。不能在未说明事务边界的情况下，把两个独立连接／存储拼接后宣称语义等价。

本地 `SQLiteRepository` 初始化会执行其参考建表 SQL；不得通过给 `database_path` 指向 B03 数据库来假定完成适配。应使用显式的 `create_app(repository=adapter)`，真实迁移由其归属方执行。
