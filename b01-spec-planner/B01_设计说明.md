# B01 设计说明

## 1. 职责与边界

B01（SpecPlannerAgent）承接两份团队文档中明确指定给规格规划 Agent 的工作：

第一部分 14.1：定义范围和需求编号；整理可验收需求；设计 R1 交接包、需求变更记录和后续任务字段；交付需求规格章节、R1 JSON 示例、需求追溯表和变更模板。

第二部分 10.1：完善平台及案例 S1/C1；定义任务 schema、需求覆盖与 DAG 生成校验；维护设计变更和集成清单；交付 T01—T11 标准任务包和需求—设计—任务—测试映射；实现 `task_planner` 与 `plan_validator`。

本参考实现只产出规格、计划、追溯和校验结果。它不写 B02 的任务状态，不写 B03 的黑板存储，不调用模型或执行开发任务，也不把模型回复当作测试通过。

## 2. 版本与来源

| 版本 | 值 | 来源 |
| --- | --- | --- |
| `requirements_version` | `R1-REFERENCE-v1.0` | 第一部分 9.3、10、11 |
| `spec_version` | `S1-v1.0` | 第二部分表 1、2.2.2 |

| `plan_version` | `PLAN-v1.0` | 第二部分 4.3.1 |

源文件 SHA-256 写入 `r1.json` 和 `s1.json`/`c1.json` 的 `source.sha256`。当前文档为准；B04 分支 `c1_contract.json` 中记录的是其早期快照哈希，属于历史证据，不作为本包的来源哈希。

## 3. 数据契约

### 3.1 需求层

`r1.json` 保留 LR-01—LR-05 五项案例需求，并区分 `FR/NFR`（编排系统自身）与 `LR`（案例业务）。`blocking_open_questions` 为空；校园统一身份认证作为非阻断开放问题 `OQ-UAA`。

`human_confirmation.status` 为 `PENDING`，六名成员均为 `PENDING`。这是刻意设置：团队文档中的示例不构成真实确认记录。

### 3.2 设计层

`s1.json` 按模块给出数据模型、约束、环境约束和开放问题。`design_entries.json` 给出 14 个设计条目，其中 6 个来自第二部分的业务/公共规则，8 个为 B03 对齐单确认纳入追溯的 `DS-B03-01`—`DS-B03-08`。

### 3.3 契约层

`c1.json` 固定 11 个 HTTP JSON 操作、错误映射、字段边界和成功/失败响应包络。字段与第二部分 2.2.3 一致，并与 B04 参考后端使用的操作清单一致。

### 3.4 计划层

`plan.json` 生成 T01—T11 标准任务包。关键串行链为：

`T01 → T02 → T03 → T04 → T05 → T10 → T11`

T01 完成后，T02、T06、T09 可并行准备；T10 直接依赖 T03—T09 全部通过。前端三个任务按同一 FE-01 资源排队，不在任务图中互相依赖。

## 4. 校验规则

`plan_validator` 检查：

1. 计划顶层版本字段与任务版本一致。
2. 20 个标准任务字段齐全且类型正确。
3. `task_id` 唯一；`outputs` 全局唯一主责。
4. `req_refs` 不越界，LR-01—05 全部覆盖。
5. `depends_on` 指向存在的任务，无自依赖，DAG 无环。
6. 关键链顺序成立，T01 无前置，T10 等待 T03—T09。
7. T04 必须包含 `TC-P01/TC-P02/TC-P03`；T09 必须包含直接调用接口的 `TC-P02`。
8. `capability` 只允许 `orchestrator`、`DB-01`、`BE-01`、`FE-01`、`QA-01`。

校验结果兼容 B06 `plan.py` 的核心字段：`ok`、`reasons`、`topological_order`。

## 5. T01 冻结门槛

`baseline.register_baseline()` 默认要求：

- 计划校验通过；
- C1 操作清单和错误映射存在且一致；
- R1 覆盖 LR-01—05 且阻断问题为空；
- S1 版本与计划一致；
- 六人确认状态全部为 `CONFIRMED`；
- 5 个基线资产文件均可读并计算 SHA-256。

当前 R1 未确认，因此 CLI 不传 `--allow-reference` 会失败。传入后生成 `REFERENCE_FROZEN` 清单并明确警告。真实确认后，把 `r1.json` 的 `status` 与六人状态改为 `CONFIRMED`，补充 `approval_ref`，再重新冻结即可得到 `FROZEN`。

## 6. 变更控制

任何 S1/C1 行为变更都必须先按 `docs/change_request_template.md` 登记 `change_request`，经六人确认后建立 `R2/S2/C2` 或新版本，并重跑：

1. `python run_checks.py all --allow-reference`；
2. `plan_validator`；
3. B03/B04/B05/B06 的接口一致性检查。

B01 不通过修改任务验收条件来让失败任务通过。
